# Security Specification

**Status:** Draft
**Version:** 0.1.0
**Last Updated:** 2026-03-28

## 1. Overview

Security in the AI-Native Messaging (AINM) protocol means that every message is cryptographically signed by its sender, and every recipient can independently verify that the message is authentic and unmodified. There are no unsigned messages in AINM. If a message cannot be verified, it is rejected. This is the protocol's primary defense against impersonation, tampering, and replay attacks.

AINM's security model builds directly on the identity system defined in `identity.md`. Every participant has an Ed25519 key pair bound to their AINM address. The sender signs each message with their private key; the recipient resolves the sender's public key via identity resolution and verifies the signature. The signing procedure uses RFC 8785 (JSON Canonicalization Scheme) to produce a deterministic byte representation of the message, ensuring that any conforming implementation will produce the same canonical form for the same logical message.

Beyond integrity and authenticity, AINM provides **trust annotations** -- a structural mechanism for distinguishing content authored by humans, generated by AI agents, and emitted by the protocol system. Each content block within a message carries a `source` field (`"user"`, `"agent"`, or `"system"`) that is covered by the message signature and therefore tamper-evident. This gives agents receiving messages a reliable signal for separating user input from system instructions -- a protocol-level defense against prompt injection attacks.

## 2. Terminology

| Term | Definition |
|------|-----------|
| **Signature** | A 64-byte Ed25519 digital signature computed over the canonical form of a message. Encoded as base64url without padding. |
| **Signing** | The process of producing a signature for a message using the sender's Ed25519 private key. |
| **Verification** | The process of confirming that a message's signature was produced by the holder of the claimed sender's private key, using their public key. |
| **Canonical Form** | The deterministic JSON serialization of a message produced by RFC 8785 (JSON Canonicalization Scheme). Used as the signing input. |
| **Trust Annotation** | The `source` field on a content block that identifies whether the content was authored by a user, generated by an agent, or produced by the system. |
| **Content Source** | The value of the `source` field: `"user"`, `"agent"`, or `"system"`. |
| **Message Envelope** | The complete JSON object containing routing fields, metadata, content blocks, and the signature. The unit of signing and delivery. |
| **Signing Input** | The UTF-8 byte encoding of the canonical form of the message (with the `signature` field removed). This is the byte sequence that is signed and verified. |

## 3. Message Envelope

The message envelope is the fundamental unit of communication in AINM. Every message sent through the protocol -- whether a text message, thread creation, or presence update -- uses this envelope structure.

### 3.1 Envelope Structure

```json
{
  "id": "019580a1-7b3e-7000-8000-abcdef123456",
  "from": "alice@messaging.example.com",
  "thread_id": "019580a0-1234-7000-8000-000000000001",
  "timestamp": "2026-03-28T12:34:56.789Z",
  "type": "message",
  "content": [
    {
      "type": "text",
      "version": "1.0",
      "source": "user",
      "text": "Hello, can you help me?",
      "fallback": "Hello, can you help me?"
    }
  ],
  "signature": "dGhpcyBpcyBhIGJhc2U2NHVybCBlbmNvZGVkIGVkMjU1MTkgc2lnbmF0dXJl"
}
```

### 3.2 Field Definitions

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `id` | string | REQUIRED | Message identifier. MUST be a UUIDv7 (RFC 9562), which provides time-ordering for natural chronological sorting and efficient deduplication. |
| `from` | string | REQUIRED | The sender's AINM address (see `identity.md`). Used to resolve the sender's public key for signature verification. |
| `thread_id` | string | REQUIRED | The UUIDv7 of the target thread. Messages are addressed to threads, not individual participants. All thread members receive the message. |
| `timestamp` | string | REQUIRED | The time the message was created by the sender. MUST be RFC 3339 format with millisecond precision and UTC timezone (`Z` suffix). Example: `"2026-03-28T12:34:56.789Z"`. |
| `type` | string | REQUIRED | Message type discriminator. Determines how the message is processed. |
| `content` | array | REQUIRED | Array of typed content blocks. Each block has its own `type`, `version`, `source`, and `fallback` fields. May be empty for non-message types (e.g., `thread.leave`). Content block schemas are defined in `content.md`. |
| `signature` | string | REQUIRED | Base64url-encoded (no padding, RFC 4648 Section 5) Ed25519 signature over the canonical form of the message with this field removed. Exactly 64 bytes when decoded. |

### 3.3 Message Types

| Type Value | Description |
|-----------|-------------|
| `message` | A standard message containing one or more content blocks. |
| `thread.create` | Creates a new thread or sub-thread. |
| `thread.join` | A participant joins an existing thread. |
| `thread.leave` | A participant leaves a thread. |
| `presence.update` | Updates the sender's presence status within a thread. |

All message types use the same envelope structure and the same signing procedure. The `type` field determines how servers and clients process the message, but the cryptographic handling is uniform.

## 4. Signing Procedure

Every message sent through the protocol MUST be signed by the sender. This section defines the exact procedure for producing a signature.

### 4.1 Step-by-Step Procedure

**Step 1: Construct the message without a signature**

Build the complete message object with all fields (`id`, `from`, `thread_id`, `timestamp`, `type`, `content`) but do NOT include the `signature` field.

```json
{
  "id": "019580a1-7b3e-7000-8000-abcdef123456",
  "from": "alice@messaging.example.com",
  "thread_id": "019580a0-1234-7000-8000-000000000001",
  "timestamp": "2026-03-28T12:34:56.789Z",
  "type": "message",
  "content": [
    {
      "type": "text",
      "version": "1.0",
      "source": "user",
      "text": "Hello!",
      "fallback": "Hello!"
    }
  ]
}
```

**Step 2: Canonicalize using RFC 8785 (JSON Canonicalization Scheme)**

Apply the following transformations to produce a deterministic JSON string:

1. **Sort all object keys** lexicographically by comparing their UTF-16 code unit values. This applies recursively to all nested objects (including objects within the `content` array).
2. **Remove all insignificant whitespace** between JSON tokens (no spaces after colons or commas, no newlines or indentation).
3. **Serialize numbers** using ECMAScript `Number.toString()` rules: no trailing zeros after the decimal point, no leading zeros before it (except `0.x`), exponential notation for very large or very small values.
4. **Serialize strings** with minimal escaping: only `\"`, `\\`, and control characters (U+0000 through U+001F) as `\uXXXX`. Other characters are passed through as-is (including non-ASCII Unicode characters).
5. **Preserve array ordering.** Arrays are NOT sorted -- the `content` array maintains its original order.

**Step 3: Encode as UTF-8 bytes**

Convert the canonical JSON string to a byte sequence using UTF-8 encoding. This byte sequence is the **signing input**.

**Step 4: Sign with Ed25519**

Sign the UTF-8 bytes using the sender's Ed25519 private key per RFC 8032. This produces a 64-byte signature.

**Step 5: Encode the signature as base64url**

Encode the 64-byte signature using base64url encoding without padding (RFC 4648 Section 5). The result is an 86-character string.

**Step 6: Insert the signature**

Add the encoded signature as the `signature` field in the message object. The message is now ready for transmission.

### 4.2 Worked Example

This example walks through signing a concrete message using a test key pair (see Section 10 for the full test key pair).

**Input message (before signing):**

```json
{
  "id": "019580a1-7b3e-7000-8000-abcdef123456",
  "from": "alice@messaging.example.com",
  "thread_id": "019580a0-1234-7000-8000-000000000001",
  "timestamp": "2026-03-28T12:34:56.789Z",
  "type": "message",
  "content": [
    {
      "type": "text",
      "version": "1.0",
      "source": "user",
      "text": "Hello!",
      "fallback": "Hello!"
    }
  ]
}
```

**After RFC 8785 canonicalization (single line, sorted keys):**

```
{"content":[{"fallback":"Hello!","source":"user","text":"Hello!","type":"text","version":"1.0"}],"from":"alice@messaging.example.com","id":"019580a1-7b3e-7000-8000-abcdef123456","thread_id":"019580a0-1234-7000-8000-000000000001","timestamp":"2026-03-28T12:34:56.789Z","type":"message"}
```

Note the key changes from canonicalization:
- Top-level keys are sorted: `content`, `from`, `id`, `thread_id`, `timestamp`, `type`
- Content block keys are sorted: `fallback`, `source`, `text`, `type`, `version`
- `version` value `"1.0"` remains a string (not converted to a number)
- All whitespace removed

**Signing input:** The above canonical string encoded as UTF-8 bytes (262 bytes for this example).

**Signature (using test key pair from Section 10):** The Ed25519 signature over these bytes, base64url-encoded, produces an 86-character string.

**Final signed message:**

```json
{
  "id": "019580a1-7b3e-7000-8000-abcdef123456",
  "from": "alice@messaging.example.com",
  "thread_id": "019580a0-1234-7000-8000-000000000001",
  "timestamp": "2026-03-28T12:34:56.789Z",
  "type": "message",
  "content": [
    {
      "type": "text",
      "version": "1.0",
      "source": "user",
      "text": "Hello!",
      "fallback": "Hello!"
    }
  ],
  "signature": "<base64url-encoded-64-byte-ed25519-signature>"
}
```

## 5. Verification Procedure

Every message received through the protocol MUST be verified before processing. This section defines the exact procedure.

### 5.1 Step-by-Step Procedure

**Step 1: Extract the signature**

Read the `signature` field value from the received message.

**Step 2: Remove the signature field**

Create a copy of the message object with the `signature` field removed. All other fields remain exactly as received.

**Step 3: Resolve the sender's public key**

Using the `from` field, resolve the sender's identity per the procedure in `identity.md` Section 4. This returns the sender's current public key and key history.

If the message's `timestamp` is older than the current key's activation time, or if verification with the current key fails, check the `key_history` array for a key that was valid at the message's timestamp (see `identity.md` Section 6.7 for the historical key lookup procedure).

**Step 4: Canonicalize**

Apply RFC 8785 canonicalization to the message object (without the signature field). This MUST produce an identical canonical form to what the sender produced in Step 2 of the signing procedure.

**Step 5: Encode as UTF-8 bytes**

Convert the canonical JSON string to UTF-8 bytes. This produces the same signing input that the sender signed.

**Step 6: Decode the signature**

Decode the base64url signature string to raw bytes. The result MUST be exactly 64 bytes. If decoding produces a different length, reject the message.

**Step 7: Verify the Ed25519 signature**

Verify the 64-byte signature against the sender's public key and the UTF-8 signing input bytes using Ed25519 verification per RFC 8032.

### 5.2 Verification Outcomes

| Outcome | Action |
|---------|--------|
| Signature valid | Process the message normally. |
| Signature invalid (current key) | Try historical keys (Step 3). If all fail, reject with error `-32010`. |
| Sender identity cannot be resolved | Reject the message with error `-32011`. |
| Sender's key marked as `compromised` | Verify signature (it may still be mathematically valid), but flag the message. Clients SHOULD display a warning. |
| Signature field missing | Reject the message with error `-32013`. |
| Signature not 64 bytes after decoding | Reject the message with error `-32010`. |

### 5.3 Normative Requirements

- Implementations MUST reject messages with invalid signatures.
- Implementations MUST reject messages where the `from` address cannot be resolved.
- Implementations MUST reject messages where the `signature` field is missing.
- Implementations SHOULD log verification failures with the message `id`, `from` address, and failure reason for debugging.
- Implementations SHOULD cache resolved identity records to avoid repeated resolution requests during high-throughput message delivery.

## 6. Trust Annotations

Trust annotations are a structural mechanism for identifying the origin type of content within a message. They enable agents to distinguish between content authored by a human, content generated by another agent, and protocol-level system content.

### 6.1 The Source Field

Every content block in a message's `content` array carries a `source` field. This field is set by the sender and is included in the message signature, making it tamper-evident.

| Source Value | Meaning | Who sets it |
|-------------|---------|-------------|
| `"user"` | Content authored directly by a human participant. | Human participants set this on their content blocks. |
| `"agent"` | Content generated by an AI agent. | Agent participants set this on their content blocks. |
| `"system"` | Protocol-level content: join/leave notifications, system instructions, thread metadata updates. | Set by servers or by participants sending protocol-level messages. |

### 6.2 Source Field Rules

- The `source` field is REQUIRED on every content block.
- The `source` field MUST be one of the three values: `"user"`, `"agent"`, or `"system"`.
- The `source` field is covered by the message `signature`. Modifying the `source` value invalidates the signature.
- A single message MAY contain content blocks with different `source` values (see Section 6.4 for examples).

### 6.3 Anti-Prompt-Injection Guidance

Trust annotations provide a protocol-level defense against prompt injection attacks. The key principle: **agents can inspect the `source` field to determine how to treat each content block.**

Recommended behavior for agent implementations:

- **`source: "user"` blocks**: Treat as user input. This is the human's message to the agent.
- **`source: "agent"` blocks**: Treat as another agent's output. Useful in multi-agent conversations where agents collaborate.
- **`source: "system"` blocks**: Treat as privileged instructions -- but ONLY if the sender is a trusted entity. An agent SHOULD verify the `from` field against a list of trusted system senders before elevating system instructions.

This separation is structural, not heuristic. An agent does not need to guess whether a piece of text is a user message or a system instruction -- the `source` field declares it, and the signature guarantees the declaration was made by the actual sender.

**Important limitation:** Trust annotations prevent tampering (a man-in-the-middle cannot change `source: "user"` to `source: "system"`), but they do not prevent a malicious sender from lying about their own source. A malicious agent could set `source: "user"` on its generated content. To defend against this, implementations SHOULD cross-check the `source` field against the sender's `type` from identity resolution:

- If `from` resolves to `type: "agent"` but a content block has `source: "user"`, the content may be misattributed.
- If `from` resolves to `type: "human"` but a content block has `source: "agent"`, the content may be misattributed.

Clients MAY display a warning when `source` and sender `type` are inconsistent.

### 6.4 Mixed-Source Message Example

A message containing both a system instruction and a user question, sent in a thread where a human is interacting with an agent:

```json
{
  "id": "019580b2-4c5d-7000-8000-222222222222",
  "from": "system@messaging.example.com",
  "thread_id": "019580a0-1234-7000-8000-000000000001",
  "timestamp": "2026-03-28T12:35:00.000Z",
  "type": "message",
  "content": [
    {
      "type": "text",
      "version": "1.0",
      "source": "system",
      "text": "You are a helpful weather assistant. Answer questions about weather only.",
      "fallback": "[system instruction]"
    },
    {
      "type": "text",
      "version": "1.0",
      "source": "user",
      "text": "What's the weather in Madrid?",
      "fallback": "What's the weather in Madrid?"
    }
  ],
  "signature": "c3lzdGVtLW1peGVkLXNvdXJjZS1leGFtcGxlLXNpZ25hdHVyZQ"
}
```

An agent receiving this message can process the blocks differently:
- The `source: "system"` block sets behavioral constraints (if the sender is trusted).
- The `source: "user"` block is the actual user query to answer.

### 6.5 Agent-to-Agent Trust

In multi-agent conversations, agents send messages with `source: "agent"` on their content blocks. Other agents receiving these messages know the content is machine-generated and can apply appropriate handling (e.g., treating it as structured data rather than natural language input).

```json
{
  "id": "019580c3-8e9f-7000-8000-333333333333",
  "from": "weather-bot@agents.example.com",
  "thread_id": "019580a0-1234-7000-8000-000000000001",
  "timestamp": "2026-03-28T12:35:02.500Z",
  "type": "message",
  "content": [
    {
      "type": "text",
      "version": "1.0",
      "source": "agent",
      "text": "Current weather in Madrid: 22C, sunny, humidity 45%.",
      "fallback": "Current weather in Madrid: 22C, sunny, humidity 45%."
    }

}
```

## 7. Deduplication

AINM uses at-least-once delivery semantics. The same message MAY be delivered more than once due to network interruptions during delivery acknowledgment, client reconnections, or server-to-server relay retries. Implementations MUST handle duplicate messages gracefully.

### 7.1 Deduplication Mechanism

The message `id` field (a UUIDv7 per RFC 9562) serves as the deduplication key.

- **Clients** MUST track received message IDs and silently discard messages whose `id` has already been seen and processed.
- **Servers** MUST track delivered message IDs per client session and avoid re-delivering messages the client has already acknowledged.

### 7.2 Deduplication Window

Implementations SHOULD maintain a deduplication window of at least:
- **10,000 message IDs**, or
- **24 hours** of message IDs (based on the UUIDv7 timestamp component),

whichever is larger.

UUIDv7's time-ordered structure enables efficient sliding-window deduplication: older IDs can be evicted based on their embedded timestamp without maintaining a full set. Implementations MAY use a time-bucketed set or a bloom filter for memory-efficient deduplication at scale.

### 7.3 Server-Side Deduplication

Servers MUST NOT re-deliver a message to a client that has already acknowledged receipt of that message within the current session. If a client reconnects and requests message replay (for messages missed during disconnection), the server SHOULD use the client's last-seen message ID to determine the replay starting point.

## 8. Error Handling

Security-related failures use JSON-RPC 2.0 error codes in the range `-32010` to `-32019`.

### 8.1 Error Code Table

| Code | Name | Description | When Returned |
|------|------|-------------|---------------|
| `-32010` | Invalid Signature | The message signature failed Ed25519 verification against all candidate keys (current and historical). | Server rejects incoming message, or client rejects received message. |
| `-32011` | Unknown Sender | The `from` address could not be resolved via identity resolution. The provider returned 404 or the domain is unreachable. | Server or client cannot verify message because sender identity is unknown. |
| `-32012` | Revoked Key | The message was signed with a key that has `revocation_reason: "compromised"` in the sender's key history. The signature may be mathematically valid, but the key is not trustworthy. | Server or client detects use of a compromised key. |
| `-32013` | Malformed Message | The message is missing required fields (`id`, `from`, `thread_id`, `timestamp`, `type`, `content`, `signature`) or contains fields with invalid formats. | Server rejects incoming message during structural validation. |

### 8.2 Error Response Format

Errors are returned as JSON-RPC 2.0 error responses:

```json
{
  "jsonrpc": "2.0",
  "id": 42,
  "error": {
    "code": -32010,
    "message": "Invalid signature: Ed25519 verification failed",
    "data": {
      "message_id": "019580a1-7b3e-7000-8000-abcdef123456",
      "from": "alice@messaging.example.com",
      "keys_tried": 2
    }
  }
}
```

The `data` field is OPTIONAL and MAY contain additional diagnostic information. Implementations SHOULD include the failing message's `id` and `from` fields to aid debugging.

## 9. Security Considerations

### 9.1 Replay Attacks

A replay attack occurs when an attacker re-transmits a previously valid signed message. AINM mitigates replay attacks through multiple layers:

1. **Message ID uniqueness:** Each message has a unique UUIDv7 `id`. Deduplication (Section 7) ensures that a replayed message is silently discarded.
2. **Timestamp validation:** Implementations SHOULD reject messages with timestamps more than **5 minutes in the future** or more than **24 hours in the past** relative to the receiver's clock. This bounds the window for replay attempts.
3. **Thread context:** A replayed message targets a specific `thread_id`. If the thread state has advanced (e.g., the conversation has moved on), the replayed message may be contextually irrelevant even if not cryptographically detected.

### 9.2 Signature Stripping

An attacker could attempt to remove the `signature` field from a message to bypass verification. The protocol prevents this:

- The `signature` field is REQUIRED on all messages.
- Implementations MUST reject any message where the `signature` field is absent.
- There is no "unsigned mode" or "debug mode" in the protocol. Every message is signed, always.

### 9.3 Trust Annotation Spoofing

A malicious participant could set `source: "user"` on content they generated (as an agent) or `source: "system"` on content that is not a legitimate system instruction. The protocol addresses this through cross-checking:

- The `from` field identifies the actual sender and is covered by the signature.
- The sender's `type` (human or agent) is available via identity resolution.
- Implementations SHOULD cross-check `source` values against the sender's `type`:
  - A `type: "agent"` sender producing `source: "user"` content is suspicious.
  - A `type: "human"` sender producing `source: "system"` content is suspicious.
- Clients SHOULD flag or warn users when source/type mismatches are detected.

### 9.4 Canonicalization Attacks

An attacker could attempt to craft a message that has a different logical meaning but produces the same canonical form (a collision). RFC 8785 is designed to be deterministic and injective -- the same logical JSON always produces the same canonical form, and different logical JSON always produces different canonical forms. However, implementations MUST use a correct RFC 8785 implementation. Specifically:

- Key sorting MUST use UTF-16 code unit comparison, not UTF-8 byte comparison. These differ for characters outside the Basic Multilingual Plane (e.g., emoji, some CJK characters).
- Number serialization MUST follow ECMAScript rules exactly. The number `1.0` serializes as `1`, and `-0` serializes as `0`.

### 9.5 Key Compromise and Forward Security

AINM v1 does not provide forward secrecy. If a participant's private key is compromised, all messages previously signed with that key can be verified by anyone holding the key -- but they could already be verified by anyone holding the public key, since signatures are publicly verifiable.

The greater risk is impersonation: an attacker with a compromised private key can sign new messages as the victim. The mitigation is immediate key rotation with `revocation_reason: "compromised"` (see `identity.md` Section 7.2).

Future protocol versions MAY introduce ephemeral key exchange for forward-secret channels.

```json
      "language": "json",
      "code": "{\"city\":\"Madrid\",\"temp_c\":22}",
      "fallback": "Madrid: 22C"
    }
  ]
}
```

**Expected canonical form:**

```
{"content":[{"fallback":"Here is the weather data:","source":"agent","text":"Here is the weather data:","type":"text","version":"1.0"},{"code":"{\"city\":\"Madrid\",\"temp_c\":22}","fallback":"Madrid: 22C","language":"json","source":"agent","type":"code","version":"1.0"}],"from":"weather-bot@agents.example.com","id":"01935801-0000-7000-8000-000000000003","thread_id":"01935800-0000-7000-8000-000000000001","timestamp":"2026-01-01T00:00:02.000Z","type":"message"}
```

Note:
- The `content` array order is preserved (text block first, code block second). Arrays are NOT sorted.
- Within each content block, keys ARE sorted: `code`, `fallback`, `language`, `source`, `type`, `version` for the code block.
- The escaped quotes inside the `code` field (`\"`) are part of the string value and remain as `\"` in the canonical form.
