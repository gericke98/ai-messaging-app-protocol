**Document structure** (per D-02, developer-friendly prose, RFC keywords only for normative statements):

### 1. Overview (2-3 paragraphs)
- What identity means in AINM: every participant (human or agent) has a unique address
- How identity fits into the protocol (addresses are used in message envelopes, thread participant lists, presence)
- Design philosophy: uniform addressing (D-08) -- protocol treats humans and agents equally

### 2. Terminology
Define: identity, address, provider, participant, key pair, key rotation, identity record

### 3. Address Format (IDNT-01, IDNT-02)
- Format: `name@provider` (per D-05)
- `name`: alphanumeric + hyphens + underscores, case-insensitive, 1-64 characters. Regex: `^[a-zA-Z0-9][a-zA-Z0-9._-]{0,63}$`
- `provider`: valid domain name (RFC 1035)
- Full address: `^[a-zA-Z0-9][a-zA-Z0-9._-]{0,63}@[a-zA-Z0-9]([a-zA-Z0-9-]*[a-zA-Z0-9])?(\\.[a-zA-Z0-9]([a-zA-Z0-9-]*[a-zA-Z0-9])?)*$`
- Uniform format: no syntactic distinction between human and agent addresses (IDNT-02)
- JSON example of parsing: `"alice@messaging.example.com"` -> `{ "name": "alice", "provider": "messaging.example.com" }`

### 4. Identity Resolution (IDNT-04, IDNT-03)
- Endpoint: `GET https://{provider}/.well-known/ainm/{name}` (per D-05)
- TLS 1.3 required
- Response Content-Type: `application/json`
- Response body (per D-06):
```json
{
  "id": "bob@agents.example.com",
  "public_key": "<base64url-encoded-Ed25519-public-key-32-bytes>",
  "server": "wss://agents.example.com/ainm/v1",
  "type": "agent",
  "agent_card_url": "https://agents.example.com/.well-known/agent-card.json",
  "key_history": []
}
```
- Field definitions:
  - `id` (string, REQUIRED): Full address, MUST match `{name}@{provider}`
  - `public_key` (string, REQUIRED): Base64url-encoded (no padding, RFC 4648 Section 5) Ed25519 public key (32 bytes raw)
  - `server` (string, REQUIRED): WebSocket endpoint URL for the participant's home server
  - `type` (string, REQUIRED): Either `"human"` or `"agent"` (per D-08). Protocol treats both equally; clients MAY adapt UI
  - `agent_card_url` (string, OPTIONAL): URL to A2A-compatible Agent Card. Present when `type` is `"agent"`, omitted for humans
  - `key_history` (array, REQUIRED): Array of previous key records (may be empty)
- Error responses: 404 (identity not found), 410 (identity deleted/revoked), with JSON-RPC style error body `{ "error": { "code": -32001, "message": "Identity not found" } }`
- Caching: servers SHOULD set `Cache-Control` headers. Clients MUST respect cache directives. Recommended TTL: 3600 seconds (1 hour) for active identities.

### 5. Identity Registration (IDNT-04)
- Endpoint: `POST https://{provider}/.well-known/ainm/register`
- Request body:
```json
{
  "name": "alice",
  "public_key": "<base64url-encoded-Ed25519-public-key>",
  "type": "human"
}
```
- Response (201 Created):
```json
{
  "id": "alice@messaging.example.com",
  "public_key": "<base64url-encoded-Ed25519-public-key>",
  "server": "wss://messaging.example.com/ainm/v1",
  "type": "human",
  "key_history": []
}
```
- Error: 409 (name already taken), 400 (invalid key format, invalid name)
- Registration does NOT include domain verification in v1 -- providers manage their own namespace
- Provider MAY require additional authentication (out of scope for protocol spec)

### 6. Key Rotation (IDNT-05, IDNT-03)
- Endpoint: `POST https://{provider}/.well-known/ainm/{name}/rotate`
- Request includes new public key + signature with CURRENT private key (proof of ownership)
- Request body:
```json
{
  "new_public_key": "<base64url-encoded-new-Ed25519-public-key>",
  "proof": "<base64url-encoded-Ed25519-signature-of-new_public_key-signed-with-current-private-key>"
}
```
- Server moves current key to `key_history` with `valid_until` set to current timestamp
- Key history record structure (per D-07):
```json
{
  "public_key": "<previous-key>",
  "valid_from": "2026-01-01T00:00:00Z",
  "valid_until": "2026-03-28T12:00:00Z",
  "revocation_reason": "scheduled_rotation"
}
```
- `revocation_reason`: `"scheduled_rotation"`, `"compromised"`, or `"administrative"`
- Overlap period: old key remains valid for verification (not signing) for 24 hours after rotation
- Verification with historical keys: try current key first, if signature fails AND message timestamp falls within a historical key's validity period, try that key
- Servers SHOULD retain key history for at least 1 year

### 7. Security Considerations
- Provider trust: providers are trusted to accurately associate public keys with identities
- Key compromise: if a key is compromised, rotation with `revocation_reason: "compromised"` signals recipients to treat messages signed with the compromised key as potentially forged
- Address enumeration: providers MAY rate-limit resolution requests to prevent mass enumeration
- TLS requirement: resolution over HTTP (not HTTPS) MUST be rejected by clients

### 8. Examples
- Full end-to-end flow: register identity -> resolve identity -> verify key -> establish connection
- Key rotation flow: rotate key -> verify old message with historical key

Include Mermaid sequence diagram for identity resolution flow.

Write `spec/security.md` following the same document structure pattern.

**Document structure:**

### 1. Overview (2-3 paragraphs)
- What security means in AINM: every message is cryptographically signed, every signature is verifiable
- How security builds on identity: signatures use Ed25519 keys bound to identities
- Trust annotations: structural separation of user/agent/system content (anti-prompt-injection)

### 2. Terminology
Define: signature, signing, verification, canonical form, trust annotation, content source, message envelope, signing input

### 3. Message Envelope (D-09)
- Define the complete message envelope structure used for signing:
```json
{
  "id": "019580a1-7b3e-7000-8000-abcdef123456",
  "from": "alice@messaging.example.com",
  "thread_id": "019580a0-1234-7000-8000-000000000001",
  "timestamp": "2026-03-28T12:34:56.789Z",
  "type": "message",
  "content": [
    {
      "type": "text",
      "version": "1.0",
      "source": "user",
      "text": "Hello, can you help me?",
      "fallback": "Hello, can you help me?"
    }
  ],
  "signature": "<base64url-encoded-ed25519-signature>"
}
```
- Field definitions:
  - `id` (string, REQUIRED): UUIDv7 (RFC 9562). Time-ordered, enables deduplication (D-12)
  - `from` (string, REQUIRED): Sender's AINM address (see identity.md)
  - `thread_id` (string, REQUIRED): UUIDv7 of the target thread (D-11)
  - `timestamp` (string, REQUIRED): RFC 3339 with millisecond precision, UTC timezone (`Z` suffix)
  - `type` (string, REQUIRED): Message type discriminator. Values: `"message"`, `"thread.create"`, `"thread.join"`, `"thread.leave"`, `"presence.update"`
  - `content` (array, REQUIRED): Array of typed content blocks (see content.md). May be empty for non-message types
  - `signature` (string, REQUIRED): Base64url-encoded (no padding) Ed25519 signature

### 4. Signing Procedure (SECU-01, SECU-02)
Step-by-step, with concrete examples at each step:

1. **Construct** the message object WITHOUT the `signature` field
2. **Canonicalize** using RFC 8785 JSON Canonicalization Scheme:
   - Sort all object keys lexicographically by UTF-16 code unit comparison (recursive -- applies to nested objects too)
   - Remove all insignificant whitespace between tokens
   - Serialize numbers using ECMAScript `Number.toString()` rules (no trailing zeros, no leading zeros except `0.x`, exponential for very large/small)
   - Serialize strings with minimal escaping (only `\"`, `\\`, and control characters `\uXXXX`)
3. **Encode** the canonical JSON string as UTF-8 bytes
4. **Sign** the UTF-8 bytes with the sender's Ed25519 private key (RFC 8032)
5. **Encode** the 64-byte signature as base64url (RFC 4648 Section 5, no padding)
6. **Insert** the encoded signature as the `signature` field in the message

Include a **worked example** with a real message:
- Show the message before signing (without signature field)
- Show the canonical form after JCS (single line, sorted keys)
- Show the signature (example base64url value)
- Show the final signed message

### 5. Verification Procedure (SECU-03)
Step-by-step:
1. **Extract** the `signature` field value from the received message
2. **Remove** the `signature` field from the message object
3. **Resolve** the sender's identity (per identity.md) to obtain their public key
   - If message timestamp falls outside the current key's validity, check `key_history` for a matching historical key
4. **Canonicalize** the remaining message using RFC 8785 (identical procedure as signing step 2)
5. **Encode** as UTF-8 bytes
6. **Decode** the base64url signature to 64 raw bytes
7. **Verify** the Ed25519 signature against the public key and the UTF-8 bytes

- Implementations MUST reject messages with invalid signatures
- Implementations MUST reject messages where `from` address cannot be resolved
- Implementations SHOULD log verification failures for debugging

### 6. Trust Annotations (SECU-04, SECU-05)
- Every content block has a `source` field (per D-10): `"user"`, `"agent"`, or `"system"`
- `source` is set by the sender and covered by the message signature (cannot be tampered)
- Definitions:
  - `"user"`: Content authored by a human participant
  - `"agent"`: Content generated by an AI agent
  - `"system"`: Protocol-level content (join/leave notifications, system messages, instructions)
- Anti-prompt-injection: agents receiving messages can filter content blocks by `source` to distinguish human input from system instructions. An agent SHOULD treat `source: "user"` blocks as user input and `source: "system"` blocks as privileged instructions only if from a trusted sender.
- Example: message with mixed source blocks (user text + system instruction):
```json
{
  "content": [
    {
      "type": "text",
      "version": "1.0",
      "source": "system",
      "text": "You are a helpful weather assistant. Answer questions about weather only.",
      "fallback": "[system instruction]"
    },
    {
      "type": "text",
      "version": "1.0",
      "source": "user",
      "text": "What's the weather in Madrid?",
      "fallback": "What's the weather in Madrid?"
    }
  ]
}
```

### 7. Deduplication (D-12)
- At-least-once delivery: the same message MAY be delivered multiple times
- Clients MUST track received message IDs (the `id` field) and silently discard duplicates
- Servers MUST track delivered message IDs per client session
- Deduplication window: implementations SHOULD maintain at least the last 10,000 message IDs or 24 hours of IDs, whichever is larger
- UUIDv7's time-ordering enables efficient deduplication with sliding-window data structures

### 8. Error Handling
Define JSON-RPC error codes for security failures:
- `-32010`: Invalid signature
- `-32011`: Unknown sender identity (cannot resolve `from` address)
- `-32012`: Revoked key (message signed with a key marked as `compromised`)
- `-32013`: Malformed message (missing required fields)

### 9. Security Considerations
- Replay attacks: message `id` + `timestamp` + deduplication prevents replay. Implementations SHOULD reject messages with timestamps more than 5 minutes in the future or more than 24 hours in the past.
- Signature stripping: the `signature` field is REQUIRED on all messages. Messages without signatures MUST be rejected.
- Trust annotation spoofing: a malicious agent could set `source: "user"` on its own content. The `from` field (covered by signature) identifies the actual sender. Implementations SHOULD cross-check `source` against sender `type` from identity resolution.

### 10. Test Vectors
Include 2-3 test vectors with known inputs and expected outputs:
- A simple text message: canonical form + expected signature bytes (using a test Ed25519 key pair published in the spec)
- A message with Unicode content (emoji, CJK characters): canonical form showing correct UTF-16 sorting
- A message with multiple content blocks: canonical form showing array ordering preservation

Publish a test key pair in the spec:

- Public key (base64url): the corresponding Ed25519 public key
- These are ONLY for test vectors -- never use in production
