## Thread Ownership Flow

### Q1: How should thread ownership be established?

| Option | Description | Selected |
|--------|-------------|----------|
| First message creates thread on sender's server | server-a becomes origin when alice sends first message. Simple, deterministic. | ✓ |
| Explicit thread.create RPC | Separate ainm.thread.create call. More explicit but adds round-trip. | |
| Thread ID contains origin domain | Structured as domain/uuid. No explicit creation needed — origin derivable. | |

**User's choice:** First message creates thread on sender's server
**Notes:** User selected preview showing the 6-step flow from message creation to relay and response.

### Q2: Routing model?

| Option | Description | Selected |
|--------|-------------|----------|
| All through origin | Every message goes to origin first. Origin assigns ordering, fans out. Consistent ordering. | ✓ |
| Direct + notify origin | Reply goes directly to all participants AND notifies origin. Faster but ordering may diverge. | |
| You decide | Claude picks routing model matching spec. | |

**User's choice:** All through origin
**Notes:** User selected preview showing the fan-out model with 3 servers.

### Q3: How does a remote server know the origin?

| Option | Description | Selected |
|--------|-------------|----------|
| Thread ID embeds origin domain | Format: server-a.local:01JQXYZ... (domain:UUIDv7). Parseable without lookup. | ✓ |
| Thread metadata field | Explicit origin_server field in metadata. Requires propagating metadata. | |
| Relay header carries origin | Relay request includes origin_server. Learned on first relay receipt. | |

**User's choice:** Thread ID embeds origin domain
**Notes:** User selected preview showing the parsing logic.
