**Part A: main.rs federation startup**

Replace the federation mode placeholder from Plan 01 with a real `async fn run_federation(cli: Cli) -> Result<()>` function:

1. Validate required flags: `identity`, `cert`, `key`, `ca_cert` must all be `Some` when mode is set. Exit with clear error message if any missing.

2. Generate server Ed25519 keypair for server-level signing:
   ```rust
   let server_keypair = Arc::new(identity::generate_keypair(&format!("server@{}", cli.identity.as_ref().unwrap()))?);
   ```

3. Load TLS cert DER and compute fingerprint:
   ```rust
   let cert_der = tls::load_cert_der(cli.cert.as_ref().unwrap());
   let tls_fingerprint = tls::compute_cert_fingerprint(&cert_der);
   ```

4. Build ServerIdentity:
   ```rust
   let server_identity = Arc::new(identity::build_server_identity(
       cli.identity.as_ref().unwrap(),
       &server_keypair,
       cli.federation_port,
       &tls_fingerprint,
   ));
   ```

5. Build mTLS HTTP client and RelaySender:
   ```rust
   let http_client = tls::build_mtls_client(ca, cert, key);
   let remote_cache = identity::RemoteServerCache::new();
   let relay_sender = Arc::new(relay::RelaySender::new(
       http_client, server_keypair.clone(), server_id.clone(), remote_cache.clone(),
   ));
   ```

6. If `--remote` is provided, resolve remote server identity at startup:
   - Build a temporary reqwest client (with mTLS)
   - GET `https://{remote}/.well-known/ainm/server`
   - Parse response into `ServerIdentity`
   - Insert into `remote_cache`
   - Also pre-seed the identity store with the remote server's participant identities (for the demo, resolve the remote's participant via `GET https://{remote}/.well-known/ainm/{name}` or hard-code for Phase 7: if our mode is "human", register `helper@{remote_domain}` as remote agent; if "agent", register `alice@{remote_domain}` as remote human)

7. Build identity store and register local participant:
   - Mode "human": register `alice@{server_id}` (human), generate keypair
   - Mode "agent": register `helper@{server_id}` (agent), generate keypair, build agent card

8. Create broadcast channels for local delivery:
   ```rust
   let (local_delivery_tx, _) = tokio::sync::broadcast::channel::<String>(256);
   ```

9. Build FederationState:
   ```rust
   let fed_state = federation::FederationState {
       server_id: server_id.clone(),
       server_keypair: server_keypair.clone(),
       server_identity: server_identity.clone(),
       thread_registry: federation::ThreadRegistry::new(),
       identity_store: identity_store.clone(),
       remote_cache: remote_cache.clone(),
       relay_sender: Some(relay_sender.clone()),
       local_delivery_tx: local_delivery_tx.clone(),
   };
   ```

    **Listener 1: Plain TCP (local WebSocket)**
    - Use existing `server::start()` pattern but pass in the federation state so server.rs can route messages to relay
    - OR create a new `server::start_federation()` that takes additional federation params
    - Bind to `0.0.0.0:{port}`

    **Listener 2: mTLS TCP (federation relay)**
    - Build Axum Router with:
      - `GET /.well-known/ainm/server` -> `identity::server_identity_handler` with `State(server_identity.clone())`
      - `POST /ainm/v1/relay` -> `federation::relay_handler` with `State(fed_state.clone())`
    - Build mTLS ServerConfig: `tls::build_mtls_server_config(ca, cert, key)`
    - Build TLS acceptor: `tokio_rustls::TlsAcceptor::from(server_config)`
    - Bind `TcpListener` to `0.0.0.0:{federation_port}`
    - Spawn accept loop:
      ```rust
      let fed_handle = tokio::spawn(async move {

      ```

**Part B: Extend server.rs for federation-aware routing**

Modify the message handling in `handle_human_connection` (the `ainm.message.send` branch):

After verifying the human's message signature, BEFORE delivering locally to the agent via `to_agent_tx`:
1. Check if the thread is federated (has remote participants)
2. Parse the thread ID to determine origin domain via `federation::parse_origin_domain()`
3. If this server IS the origin:
   - Deliver to local participants via `to_agent_tx` (existing behavior)
   - If there are remote participating servers, enqueue relay via `relay_sender.enqueue()`
4. If this server is NOT the origin (message for a remote-origin thread):
   - Relay to the origin server instead of delivering locally
   - The origin will assign sequence and fan out back

To make federation state accessible in server.rs, extend `ServerState` with optional federation fields:
```rust
pub struct ServerState {
    // ... existing fields ...
    pub federation: Option<FederationContext>,
}

pub struct FederationContext {
    pub server_id: String,
    pub thread_registry: federation::ThreadRegistry,
    pub relay_sender: Arc<relay::RelaySender>,
    pub local_delivery_tx: tokio::sync::broadcast::Sender<String>,
}
```

When federation is `None` (legacy mode), routing works exactly as before. When `Some`, check federation routing rules.

Similarly extend `handle_agent_connection` for the agent mode: when the agent sends a response (ainm.message.send), check if it needs to be relayed to the origin server.

Also extend the `ainm.thread.create` handler: when creating a thread in federation mode, use `federation::ThreadRegistry::create_thread()` which embeds the origin domain per D-12.

Per D-01: Two terminals -- human REPL on Server A, structured logs on Server B.
Per D-02: alice@server-a.local (human) on A, helper@server-b.local (agent) on B.
Per D-03: Server B headless, terminal shows relay receipt + validation + agent processing + outgoing relay.
Per D-05: Mode configured via CLI flags.
Per D-06: No flags = legacy mode unchanged.
Per D-10/D-11: Origin server authority, all messages route through origin.

# Stage 1: Build
FROM rust:1.85-bookworm AS builder

2. Create `demo/docker-compose.yml`:

```yaml
services:
  server-a:
    build: .
    ports:
      - "8080:8080"
      - "8443:8443"
    volumes:
      - ./certs:/certs:ro
    command:
      - "--mode"
      - "human"
      - "--port"
      - "8080"
      - "--federation-port"
      - "8443"
      - "--identity"
      - "server-a.local"
      - "--cert"
      - "/certs/server-a.pem"
      - "--key"
      - "/certs/server-a-key.pem"
      - "--ca-cert"
      - "/certs/ca.pem"
      - "--remote"
      - "server-b:9443"
    networks:
      federation:
        aliases:
          - server-a.local
    stdin_open: true
    tty: true

  server-b:
    build: .
    ports:
      - "9080:9080"
      - "9443:9443"
    volumes:
      - ./certs:/certs:ro
    command:
      - "--mode"
      - "agent"
      - "--port"
      - "9080"
      - "--federation-port"
      - "9443"
      - "--identity"
      - "server-b.local"
      - "--cert"
      - "/certs/server-b.pem"
      - "--key"
      - "/certs/server-b-key.pem"
      - "--ca-cert"
      - "/certs/ca.pem"
      - "--remote"
      - "server-a:8443"
    networks:
      federation:
        aliases:
          - server-b.local
    depends_on:
      - server-a

networks:
  federation:
    driver: bridge
```

Key design decisions:
- Server A runs human mode (port 8080/8443), Server B runs agent mode (port 9080/9443). Per D-01/D-02.
- Certificates mounted as read-only volume from `demo/certs/`. Per D-07.
- Docker network aliases map `server-a.local` and `server-b.local` to container IPs. This is critical -- the `--remote` flag uses Docker service names (`server-b:9443`) for TCP connection, but the `--identity` uses the `.local` domain for identity/signing. DNS aliases make both resolvable.
- `server-a` has `stdin_open: true` and `tty: true` for the interactive REPL per D-01.
- `server-b` depends on `server-a` to ensure Server A is available when B tries to resolve its identity.
- Per D-03: Server B runs headless, its terminal shows structured federation logs.

NOTE on Docker networking pitfall (from research): Use Docker service names for `--remote`, not `localhost`. The Docker bridge network resolves `server-b` to Server B's container IP.
