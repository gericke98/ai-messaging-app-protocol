    **packages/connector/DECISIONS.md** — content template:
    ```markdown
    # Decisions — @ainm/connector

    Architectural decisions for the AINM TypeScript connector SDK. Captured during Phase 15 ratification (2026-04).

    ## D-01: RFC 8785 JCS via `canonicalize@2.0.0`
    **Decision:** Use the `canonicalize` npm package (v2.0.0, exact pin) for JSON canonicalization.
    **Rationale:** RFC 8785-conformant; predictable output; small surface; no transitive deps. Hand-rolling JCS gets ECMAScript number formatting, key sorting, and string escapes wrong (see RESEARCH.md "Don't Hand-Roll" table).
    **Alternatives considered:** Hand-rolled canonicalizer (rejected — escape handling too easy to get wrong); upgrading to canonicalize@3.0.0 (deferred to a follow-up — exact-pin floor first per RAT-06).
    **Conformance:** Phase 15 Plan 02 adds a cross-platform conformance test loading `tests/vectors/jcs_vectors.json`.

    ## D-02: Ed25519 via `@noble/ed25519@2.2.0`
    **Decision:** Use `@noble/ed25519` v2.2.0 (exact pin) with `@noble/hashes` v2.2.0 for SHA-512 sync API.
    **Rationale:** Audited 4× (most recent April 2026); 0 transitive deps; misuse-resistant API.
    **Alternatives considered:** Native Node `crypto` (rejected — Ed25519 sign produces different byte ordering than the spec without manual canonicalization); tweetnacl (rejected — older, larger surface); upgrading to @noble/ed25519@3.1.0 (deferred per Phase 15 RAT-01 — pin current floor first).

    ## D-03: WebSocket transport via `ws@8.18.0`
    **Decision:** Use the `ws` npm package for the WebSocket client; no custom transport abstraction.
    **Rationale:** De-facto standard for Node WebSocket; ergonomic with async/await wrappers; supports binary and text frames; mature close-code handling.
    **Alternatives considered:** Native `WebSocket` global (Node 22 stable but lacks ping/pong control); `socket.io` (rejected — adds protocol overhead the AINM JSON-RPC framing does not need).

    ## D-04: Single-class `AINMAgent` with method-router design
    **Decision:** SDK exposes a single `AINMAgent` class; consumers register `onMessage`/`onAction`/`onMemoryRequest` callbacks; SDK owns the JSON-RPC routing internally.
    **Rationale:** Matches MCP and A2A patterns; minimizes per-handler boilerplate; one place to enforce signing.
    **Alternatives considered:** Per-method handler classes (rejected — too much ceremony for a 5-line agent example); EventEmitter pattern (rejected — typing is poor across method args).

    ## Future decisions (Phase 16+)
    - AU-05 two-key identity split: this SDK currently exposes one keypair; Phase 16 will introduce `k_sign`/`k_conn` separation.
    - Structured logger (vs hand-rolled `log.ts`): Phase 15 Plan 05 introduces a 30-line redactor wrapper around `console.*`; pino is deferred until structured logs become a real consumer requirement.
    ```
