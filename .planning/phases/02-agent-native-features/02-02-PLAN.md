  <action>
Create `spec/interactive.md` following the Phase 1 spec document template: Overview, Terminology, numbered core sections, Error Handling, Security Considerations, Examples/References.

The specification MUST cover these sections:

**Section 1: Overview** -- Interactive content blocks extend the content block system (content.md) with UI elements that users can interact with. The protocol defines a static component catalog -- the spec IS the catalog (per D-08). Agents construct blocks from the spec, clients render from the spec. No arbitrary code execution (A2UI security model). User interactions flow back as ActionBlock messages visible to all thread participants (per D-07).

**Section 2: Terminology** -- Define: interactive block, action_id, ActionBlock, declarative component model, semantic style, component catalog, form field.

**Section 3: Declarative Component Model** -- The spec defines exactly what fields each block type has. There is no runtime component negotiation or catalog discovery. A client that supports AINM interactive blocks knows the full schema from this spec. Agents construct blocks using only the fields defined here. Unknown fields MUST be ignored by clients. This follows the A2UI approach (per D-08). Three semantic styles: `primary`, `secondary`, `danger` -- clients map these to their own design system.

**Section 4: ButtonBlock** -- Type: `"button"`. Fields (in addition to base schema):
- `label` (string, REQUIRED): Button text displayed to the user
- `action_id` (string, REQUIRED): Unique identifier within the message, referenced by ActionBlock
- `style` (string, OPTIONAL, default "primary"): One of "primary", "secondary", "danger"
- `disabled` (boolean, OPTIONAL, default false): If true, button is rendered but not clickable
- `confirmation` (string or null, OPTIONAL, default null): If non-null, client MUST show this text and require explicit approval before sending ActionBlock
Fallback format: `[Button: {label}]`
Include full JSON example.

**Section 5: FormBlock** -- Type: `"form"`. Fields:
- `action_id` (string, REQUIRED): Referenced by ActionBlock on submit
- `fields` (array, REQUIRED): Array of field objects
- `title` (string, OPTIONAL): Form heading
- `submit_label` (string, OPTIONAL, default "Submit"): Submit button text
Field object properties:
- `name` (string, REQUIRED): Field identifier, used as key in ActionBlock data
- `label` (string, REQUIRED): Display label
- `field_type` (string, REQUIRED): One of 8 types: `text`, `textarea`, `number`, `select`, `multiselect`, `checkbox`, `date`, `datetime`
- `required` (boolean, OPTIONAL, default false)
- `default` (any, OPTIONAL): Default value matching the field type
- `placeholder` (string, OPTIONAL): Hint text for text/textarea/number fields
- `validation` (string, OPTIONAL): Regex pattern for client-side validation
- `options` (array of strings, REQUIRED for select/multiselect): Available choices
Fallback format: `[Form: {title} - fields: {field names comma-separated}]`
Client MUST validate `required` fields before submission. Client SHOULD validate `validation` regex before submission.
Include full JSON example with 3+ fields of different types.

**Section 6: TableBlock** -- Type: `"table"`. Fields:
- `columns` (array, REQUIRED): Array of column definitions
- `rows` (array, REQUIRED): Array of row objects (keys match column `key` fields)
- `title` (string, OPTIONAL): Table heading
- `row_actions` (array, OPTIONAL): Action buttons per row
Column properties: `key` (string), `label` (string), `sortable` (boolean, default false), `align` (string: "left", "right", "center", default "left")
Row action properties: `action_id` (string), `label` (string), `style` (string)
Fallback format: Markdown table with headers and all rows.
Sorting is client-side only. Pagination deferred to future versions -- all rows are inline in v1.
Row action clicks trigger ActionBlock with `data` containing the row's values.
Include full JSON example with sortable columns and row actions.

**Section 7: ApprovalBlock** -- Type: `"approval"`. Fields:
- `action_id` (string, REQUIRED): Referenced by ActionBlock
- `title` (string, REQUIRED): What is being approved
- `description` (string, OPTIONAL): Details about the approval
- `status` (string, REQUIRED): One of "pending", "approved", "rejected", "changes_requested". Initial value MUST be "pending".
- `options` (array, REQUIRED): Array of option objects with `value` (string), `label` (string), `style` (string: primary/secondary/danger)
Fallback format: `[Approval: {title} - Status: {status}]`
State machine: pending -> approved | rejected | changes_requested. All terminal states are immutable. Server MUST reject ActionBlocks targeting resolved (non-pending) ApprovalBlocks with error -32071.
Include state machine diagram (ASCII art).
Include full JSON example.

**Section 8: ActionBlock** -- Type: `"action"`. This is the user response block -- sent as a NEW message in the thread when a user interacts with any interactive block. Fields:
- `ref_message_id` (string, REQUIRED): ID of the message containing the interactive block
- `ref_block_index` (integer, REQUIRED): Index of the interactive block in the referenced message's content[] array
- `action_id` (string, REQUIRED): Must match the action_id of the referenced interactive block
- `data` (object, REQUIRED): User input data. For ButtonBlock: empty object `{}`. For FormBlock: `{field_name: value}` pairs. For TableBlock row actions: row values object. For ApprovalBlock: `{value: "selected_option_value"}`.
Fallback format: `[Action: clicked '{label}']` or `[Action: submitted '{form_title}']`
ActionBlock messages use message type `"action"` (new type added in Phase 2).
ActionBlock messages are signed per security.md -- they are full messages, not ephemeral events.
Deduplication: Server MUST deduplicate by message `id` (UUIDv7).

**Section 9: Content Size Limits** -- Per CONT-05, the protocol defines NO arbitrary payload size limits. The `maxContentBlocks` and `maxMessageSize` capability flags from transport.md Section 4.3 are server-configurable, not protocol-imposed. Servers SHOULD accept messages up to 1MB by default. Servers MAY impose their own limits and communicate them during capability negotiation.

**Section 10: Error Handling** -- Error code range -32070 to -32079 for interactive content:
- `-32070`: Invalid action_id (no matching interactive block)
- `-32071`: Approval already resolved (ActionBlock targets non-pending ApprovalBlock)
- `-32072`: Form validation failed (required field missing or validation regex failed)
- `-32073`: Referenced message not found (ref_message_id invalid)
- `-32074`: Invalid block index (ref_block_index out of range)

**Section 11: Security Considerations** -- ActionBlocks are signed messages visible to all participants. This is intentional transparency (per D-07). The confirmation field on ButtonBlock provides a security gate for destructive actions. Agents cannot execute code through interactive blocks -- the declarative model prevents code injection (per D-08). Trust annotations (source field) on ActionBlocks are always "user" since they represent human input.

**Section 12: Examples** -- End-to-end example: agent sends a message with FormBlock + ApprovalBlock, user submits form (ActionBlock), another user approves (ActionBlock). Show the full message envelopes.

Style: RFC-keyword prose with inline JSON examples. Target 600-800 lines.
