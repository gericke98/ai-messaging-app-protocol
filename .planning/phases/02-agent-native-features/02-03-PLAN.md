Create `spec/agent-card.md` following the Phase 1 spec document template.

The specification MUST cover these sections:

**Section 1: Overview** -- Agent Cards are JSON documents that describe an agent's capabilities, skills, and preferences. They enable capability discovery before interaction. AINM Agent Cards are a superset of A2A Agent Cards (per D-09) -- A2A clients can read the top-level fields while AINM clients get richer information from the `ainm` extension object.

**Section 2: Terminology** -- Define: Agent Card, capability card, well-known endpoint, skill, capability, content type support, AINM extension object.

**Section 3: Discovery** -- Agent Cards are discovered through the `agent_card_url` field in the identity record (identity.md Section 4.2). Resolution flow: (1) resolve identity via `.well-known/ainm/{name}`, (2) read `agent_card_url` from identity record, (3) HTTP GET the Agent Card URL. The Agent Card URL SHOULD follow the convention `https://{provider}/.well-known/ainm/{name}/agent-card.json` but MAY be any HTTPS URL. Human identities (type: "human") do not have Agent Cards.

**Section 4: Caching** -- Per D-10, Agent Cards use standard HTTP caching with `ETag` and `If-None-Match` headers. Servers MUST include an `ETag` header on Agent Card responses. Clients SHOULD cache Agent Cards and use `If-None-Match` for conditional requests. A `304 Not Modified` response means the cached card is current. The `version` field inside the card provides an additional application-level version signal.

**Section 5: A2A-Compatible Schema** -- Top-level fields matching A2A Agent Card spec:
- `name` (string, REQUIRED): Agent display name
- `description` (string, REQUIRED): Agent description
- `url` (string, REQUIRED): Agent's primary URL
- `version` (string, REQUIRED): Agent Card version (semver)
- `protocolVersion` (string, REQUIRED): A2A protocol version for A2A compatibility
- `capabilities` (object, REQUIRED): A2A capabilities -- `streaming` (boolean), `pushNotifications` (boolean)
- `skills` (array, REQUIRED): Array of skill objects with `id`, `name`, `description`, `tags`
- `defaultInputModes` (array, OPTIONAL): MIME types the agent accepts
- `defaultOutputModes` (array, OPTIONAL): MIME types the agent produces
These fields MUST be present and valid for A2A client compatibility.

**Section 6: AINM Extension Object** -- All AINM-specific fields live under a top-level `ainm` object (per Pitfall 5 -- namespacing avoids breaking A2A validators). Fields:
- `ainm.contentTypes` (array of strings, REQUIRED): Content block types the agent can send. Values from the core set: "text", "code", "image", "file", "button", "form", "table", "approval". Plus any extension types.
- `ainm.streaming` (object, REQUIRED): `supported` (boolean), `parallelBlocks` (boolean), `preferredChunkSize` (string: "token" or "sentence")
- `ainm.threading` (object, REQUIRED): `subThreads` (boolean), `maxConcurrentThreads` (integer or null for unlimited)
- `ainm.memory` (object, REQUIRED): `archivalSupported` (boolean), `contextFramePreferred` (boolean)
- `ainm.tools` (array, REQUIRED): Array of tool objects matching MCP tool listing format (per D-12): `name` (string), `description` (string), `inputSchema` (JSON Schema object). Empty array if agent has no tools.
- `ainm.protocolVersion` (string, REQUIRED): AINM protocol version (e.g., "0.1.0")

**Section 7: Agent Card Validation** -- Clients MUST validate that required top-level fields are present. Clients SHOULD validate that the `ainm` object is present for AINM-specific features. Unknown top-level fields MUST be ignored (forward compatibility). Unknown fields within the `ainm` object MUST be ignored.

**Section 8: Error Handling** -- Error code range -32060 to -32069:
- `-32060`: Agent Card not found (404 from agent_card_url)
- `-32061`: Invalid Agent Card format (JSON parse error or missing required fields)
- `-32062`: Agent Card version mismatch (client cannot process this card version)

**Section 9: Security Considerations** -- Agent Cards are public documents. They MUST NOT contain secrets, private keys, or authentication tokens. The `agent_card_url` in the identity record is integrity-protected by the identity resolution mechanism (served over TLS from the provider). Agent Cards SHOULD be served over HTTPS. Tools listed in `ainm.tools` expose only the input schema -- output schemas and implementation details are not disclosed.

**Section 10: Examples** -- Full Agent Card JSON example with all fields. Minimal Agent Card (A2A-only fields). Agent Card for a tool-heavy agent.

Create `spec/tool-visibility.md` following the Phase 1 spec document template.

The specification MUST cover these sections:

**Section 1: Overview** -- Tool visibility makes agent tool calls transparent to all thread participants. When an agent invokes a tool, the protocol emits three types of events: ToolCallStarted, ToolCallProgress, and ToolCallCompleted. These events are persistent signed messages in the thread -- part of the audit trail. Clients render them as collapsible activity indicators. This is the core transparency principle: no opaque tool calls.

**Section 2: Terminology** -- Define: tool call, tool call lifecycle, call_id, collapsible indicator, progress (determinate vs indeterminate).

**Section 3: Tool Call Lifecycle** -- Three event types, each a signed message in the thread:

**3.1 ToolCallStarted** (message type: `"tool.call.started"`)
Message fields (in addition to standard envelope from security.md):
- `content[]`: Array with at least one TextBlock providing human-readable description of what the tool is doing. This is the fallback for clients that do not support collapsible rendering.
- `tool.call_id` (string, REQUIRED): Unique identifier for this tool call (UUIDv7 or `tc-{UUIDv7}` prefixed). All progress and completed events reference this.
- `tool.name` (string, REQUIRED): Tool name matching the Agent Card `ainm.tools[].name`
- `tool.description` (string, OPTIONAL): Human-readable description of the tool
- `tool.input` (object, REQUIRED): The input parameters passed to the tool (visible to participants)
Full JSON example showing the complete signed message envelope.

**3.2 ToolCallProgress** (message type: `"tool.call.progress"`)
Message fields:
- `content[]`: Updated human-readable progress description
- `tool.call_id` (string, REQUIRED): References the started event
- `tool.progress.current` (integer or null, OPTIONAL): Current progress count (for determinate progress)
- `tool.progress.total` (integer or null, OPTIONAL): Total expected count (null for indeterminate)
- `tool.progress.detail` (string, OPTIONAL): Text description of current progress state
Zero or more progress events may occur between started and completed. Agents SHOULD send progress events for long-running tools (>5 seconds).

**3.3 ToolCallCompleted** (message type: `"tool.call.completed"`)
Message fields:
- `content[]`: Human-readable result summary
- `tool.call_id` (string, REQUIRED): References the started event
- `tool.name` (string, REQUIRED): Tool name (repeated for standalone readability)
- `tool.result_summary` (string, REQUIRED): Brief text summary of the result
- `tool.duration_ms` (integer, REQUIRED): Wall-clock execution time in milliseconds
- `tool.status` (string, REQUIRED): "success" or "error"
- `tool.error_message` (string, OPTIONAL): Error details if status is "error"
Full JSON example.

**Section 4: Thread Visibility** -- Tool events are delivered to the thread like any other message. All thread participants receive them. There are no private tool calls in AINM. If an agent needs to use a tool without thread visibility, it must do so outside the protocol (not covered by this spec).

**Section 5: Rendering Guidance** -- Normative rendering behavior:
- Default render state: collapsed -- showing tool name + current status (e.g., "code_search: running")
- Expanded render state: shows tool input, progress details, result summary, duration
- Completed with success: green/positive indicator
- Completed with error: red/negative indicator
- Duration: clients SHOULD display human-readable duration (e.g., "1.4s")
- The `content[]` array on each event provides a TextBlock fallback for clients that do not support the collapsible rendering pattern.

**Section 6: Error Handling** -- No new error code range for tool visibility (tool events are standard signed messages; delivery errors use existing transport error codes). If a tool call fails, the agent sends a ToolCallCompleted with `status: "error"` -- this is application-level, not a protocol error.

**Section 7: Security Considerations** -- Tool events are signed by the agent that initiated the tool call. The `tool.input` field is visible to all participants -- agents MUST NOT pass sensitive data (passwords, tokens) as tool inputs. If sensitive data must be passed, agents SHOULD redact the input in the tool event and handle the sensitive data through secure channels. Tool events cannot be forged because they require a valid Ed25519 signature from the invoking agent.

**Section 8: Examples** -- Full lifecycle example: started -> 2 progress events -> completed(success). Error example: started -> completed(error). Example of rendering collapsed vs expanded states (ASCII art or description).
