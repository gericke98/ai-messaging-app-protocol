# Phase 8: Security Hardening, Reliability & Backfill - Research

**Researched:** 2026-03-28
**Domain:** Federation security (replay protection, TOFU, cert rotation), persistent queuing, thread history backfill
**Confidence:** HIGH

## Summary

Phase 8 hardens the existing federation relay from Phase 7 across three domains: security (replay protection via relay_timestamp + relay_id, TOFU key pinning, certificate rotation via tls_fingerprints array), reliability (persistent offline queue replacing in-memory VecDeque, exponential backoff surviving restarts, bounded retention), and backfill (cursor-based thread history endpoint with authorization). All three domains converge on a single new dependency: redb 3.1.1, a pure-Rust ACID embedded database that stores the dedup cache, TOFU pin store, and offline message queue in one file.

The existing codebase is well-structured for these changes. `relay.rs` has a clean `RelaySender` with per-destination queues and `BackoffState` that can be refactored to use redb-backed storage. `federation.rs` has a `relay_handler` with a clear validation pipeline where replay checks slot in before the existing triple-layer validation. `identity.rs` has `ServerIdentity` with a singular `tls_fingerprint` field that needs to become `tls_fingerprints: Vec<String>`. The Docker Compose setup already has two-server federation working, making demo scenarios for partition healing and cert rotation straightforward extensions.

**Primary recommendation:** Implement in three waves -- (1) redb persistence layer + replay protection + TOFU, (2) persistent offline queue + partition healing, (3) backfill endpoint + demo scenarios. Each wave builds on the previous and can be independently verified.

### Pattern 1: redb Table Design
**What:** Three logical tables in one redb database file
**When to use:** All Phase 8 persistence

```rust
use redb::TableDefinition;

// Offline queue: key = "{destination}:{sequence_u64_be_bytes}", value = JSON bytes
// UUIDv7 bytes as sequence gives time-ordering for FIFO and age-based cleanup
const OFFLINE_QUEUE: TableDefinition<&[u8], &[u8]> = TableDefinition::new("offline_queue");

// Dedup cache: key = relay_id (UUIDv7 string), value = relay_timestamp (RFC 3339 string)
const DEDUP_CACHE: TableDefinition<&str, &str> = TableDefinition::new("dedup_cache");

// TOFU pin store: key = server_id (string), value = pinned fingerprint (string)
const TOFU_PINS: TableDefinition<&str, &str> = TableDefinition::new("tofu_pins");
```

**Key design rationale for offline queue:**
- Composite key `{destination}:{uuidv7_bytes}` enables range scans per destination
- UUIDv7 bytes are naturally time-ordered, making FIFO drain and age-based cleanup efficient
- Using `&[u8]` keys gives full control over key structure and ordering
- Value is serialized JSON of the message envelope

### Pattern 3: Replay Protection Pipeline
**What:** Timestamp freshness check + dedup cache lookup inserted into relay_handler BEFORE existing validation
**When to use:** All inbound relay requests

```
Inbound relay -> Parse params -> Extract relay_timestamp + relay_id
  -> Check timestamp within 5-min window (reject if stale)
  -> Check dedup cache (reject if relay_id seen)
  -> Insert relay_id into dedup cache
  -> Existing triple-layer validation (FAUT-03)
  -> Process messages
```

### Pattern 4: TOFU + Fingerprint Array Verification
**What:** On TLS connection, check peer cert fingerprint against both TOFU pins AND tls_fingerprints array
**When to use:** FAUT-02 layer 1 in main.rs TLS accept loop

```
Peer connects with cert fingerprint F
  -> Look up server_id from RemoteServerCache.find_by_fingerprints(F)
  -> If found:
       -> Check TOFU pin for that server_id
       -> If no pin exists: set pin to F (first contact)
       -> If pin matches F: OK
       -> If pin != F but F is in server's tls_fingerprints alongside pinned fingerprint:
            -> Auto-update pin to F (D-09 rotation)
            -> Log rotation event
       -> If pin != F and not in array: REJECT (potential MITM)
  -> If not found: REJECT
```

### Pattern 5: Backfill Handler
**What:** JSON-RPC method handler for `ainm.backfill` on the relay endpoint
**When to use:** BKFL-01 through BKFL-04

The relay_handler already dispatches on method name. Add `ainm.backfill` as a second match arm. The handler:
1. Validates the requesting server has a participant in the thread (D-18)
2. Looks up the server's join timestamp to enforce post-join visibility (D-19)
3. Queries messages after `after_sequence` cursor, limited by `limit` param
4. Returns messages + has_more + next_cursor

**Thread message storage consideration:** The current demo stores no message history (messages are delivered and forgotten). For backfill to work, the origin server needs to persist thread messages. This requires either: (a) storing messages in redb, or (b) adding an in-memory message history buffer. Given the demo context and redb already being added, storing thread messages in redb is the natural choice.

### Anti-Patterns to Avoid
- **Sharing redb write transactions across async boundaries:** redb transactions are not `Send`. Open transaction, do work, commit -- all synchronous, wrapped in `tokio::task::spawn_blocking` or a sync block.
- **Using String keys for composite queue keys:** String concatenation for composite keys leads to ambiguous key boundaries. Use structured byte keys with fixed-length prefixes.
- **Coupling backfill to offline queue:** D-15 explicitly decouples them. Backfill is on-demand, queue drain is automatic on reconnection.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Persistent queue | Custom file format, WAL, or SQLite wrapper | redb tables with byte keys | ACID, crash-safe, MVCC concurrency, zero-copy reads, pure Rust |
| UUIDv7 generation | Custom timestamp-based ID | `uuid::Uuid::now_v7()` | Already in use; time-ordered, globally unique |
| JSON canonicalization | Custom key sorting | `serde_json_canonicalizer` (already in deps) | RFC 8785 compliant; already used for signing |
| Certificate fingerprinting | Custom hash implementation | `ring::digest::digest(&SHA256, der_bytes)` | Already in `tls.rs::compute_cert_fingerprint()` |
| Background periodic task | Custom timer loop with sleep | `tokio::time::interval(Duration::from_secs(3600))` | Drift-free, cancellable, standard Tokio pattern |

## Common Pitfalls

### Pitfall 1: redb Transactions and Async
**What goes wrong:** Holding a redb write transaction across an `.await` point causes a compile error (transaction is not `Send`) or deadlock.
**Why it happens:** redb uses internal locking that is not async-aware. Write transactions block other writers.
**How to avoid:** Keep all redb operations synchronous. Use short-lived transactions. For the async relay handler, collect needed data, then do redb operations in a synchronous block or `spawn_blocking`.
**Warning signs:** Compilation errors about `Send` bounds on redb types.

### Pitfall 2: Key Ordering in Composite Queue Keys
**What goes wrong:** Using string-based composite keys like `"server-a.local:019580a1..."` sorts lexicographically, which may interleave destinations unpredictably.
**Why it happens:** redb sorts keys by their byte representation.
**How to avoid:** Use a fixed-length destination hash prefix (e.g., 8-byte hash of destination name) followed by UUIDv7 bytes. Or use separate key prefixes that are guaranteed to group by destination. Alternatively, consider one sub-table per destination by using dynamic table names -- but redb's `TableDefinition` requires static names, so use a prefixed key approach.
**Warning signs:** Range scans returning messages from wrong destinations.

### Pitfall 3: Clock Skew Breaking Replay Protection
**What goes wrong:** Legitimate relay from a server with slightly different clock time gets rejected as "stale."
**Why it happens:** 5-minute window assumes clocks are roughly synchronized.
**How to avoid:** The 5-minute window (D-01) is generous enough to tolerate typical NTP drift (< 1 second). For Docker demo, containers share the host clock, so no issue. Log rejected timestamps for debugging.
**Warning signs:** Intermittent relay rejections with "timestamp outside replay window" errors.

### Pitfall 4: Backfill Without Message Storage
**What goes wrong:** Origin server cannot serve backfill because messages are not persisted -- they are delivered in real-time and discarded.
**Why it happens:** Current Phase 7 demo has no message history; messages flow through broadcast channels and are gone.
**How to avoid:** Add a `thread_messages` redb table that stores all messages at the origin server. This is required for BKFL-01 to work. Key: `{thread_id}:{sequence_number}`, Value: serialized message envelope.
**Warning signs:** Backfill returns empty results even for threads with activity.

### Pitfall 5: Docker Volume for redb Persistence
**What goes wrong:** DEMO-03 (partition healing) fails because redb file is inside the container and lost on restart.
**Why it happens:** Default Docker container filesystem is ephemeral.
**How to avoid:** Add a named volume or bind mount in docker-compose.yml for the redb data directory. E.g., `volumes: - server-a-data:/data`.
**Warning signs:** Queue is empty after docker-compose restart.

### Pitfall 6: ServerIdentity Struct Migration
**What goes wrong:** Changing `tls_fingerprint: String` to `tls_fingerprints: Vec<String>` breaks all existing code that reads the singular field.
**Why it happens:** Struct field rename cascades through all usages.
**How to avoid:** D-08 says clean break (no compat shim). Update all usages simultaneously: `build_server_identity()`, `server_identity_handler()`, `resolve_remote_identity()`, `find_by_fingerprint()`, JSON schema, transport.md.
**Warning signs:** Compilation errors at every site that reads `tls_fingerprint`.

## Code Examples

### redb Database Initialization
```rust
// Source: redb docs + project pattern
use redb::{Database, TableDefinition};

const OFFLINE_QUEUE: TableDefinition<&[u8], &[u8]> = TableDefinition::new("offline_queue");
const DEDUP_CACHE: TableDefinition<&str, &str> = TableDefinition::new("dedup_cache");
const TOFU_PINS: TableDefinition<&str, &str> = TableDefinition::new("tofu_pins");
const THREAD_MESSAGES: TableDefinition<&str, &[u8]> = TableDefinition::new("thread_messages");

pub fn init_database(path: &str) -> Result<Database, redb::Error> {
    let db = Database::create(path)?;
    // Create tables in an initial write transaction
    let write_txn = db.begin_write()?;
    write_txn.open_table(OFFLINE_QUEUE)?;
    write_txn.open_table(DEDUP_CACHE)?;
    write_txn.open_table(TOFU_PINS)?;
    write_txn.open_table(THREAD_MESSAGES)?;
    write_txn.commit()?;
    Ok(db)
}
```

### Replay Protection Check
```rust
// Source: project decisions D-01 through D-04
fn check_replay(
    db: &Database,
    relay_id: &str,
    relay_timestamp: &str,
) -> Result<bool, String> {
    // 1. Parse timestamp and check freshness (5-minute window)
    let ts = chrono::DateTime::parse_from_rfc3339(relay_timestamp)
        .map_err(|e| format!("Invalid timestamp: {}", e))?;
    let age = chrono::Utc::now().signed_duration_since(ts);
    if age > chrono::Duration::minutes(5) || age < chrono::Duration::minutes(-1) {
        return Err("Relay timestamp outside acceptable window".to_string());
    }

    // 2. Check dedup cache
    let write_txn = db.begin_write().map_err(|e| e.to_string())?;
    {
        let mut table = write_txn.open_table(DEDUP_CACHE).map_err(|e| e.to_string())?;
        if table.get(relay_id).map_err(|e| e.to_string())?.is_some() {
            return Err("Duplicate relay_id".to_string());
        }
        table.insert(relay_id, relay_timestamp).map_err(|e| e.to_string())?;
    }
    write_txn.commit().map_err(|e| e.to_string())?;
    Ok(true)
}
```

### TOFU Pin Check with Auto-Update
```rust
// Source: D-05, D-09
fn verify_tofu(
    db: &Database,
    server_id: &str,
    peer_fingerprint: &str,
    published_fingerprints: &[String],
) -> Result<bool, String> {
    let write_txn = db.begin_write().map_err(|e| e.to_string())?;
    let result;
    {
        let mut table = write_txn.open_table(TOFU_PINS).map_err(|e| e.to_string())?;
        match table.get(server_id).map_err(|e| e.to_string())? {
            None => {
                // First contact: pin this fingerprint
                table.insert(server_id, peer_fingerprint).map_err(|e| e.to_string())?;
                tracing::info!("[tofu] Pinned {} -> {}", server_id, peer_fingerprint);
                result = true;
            }
            Some(pinned) => {
                let pinned_fp = pinned.value().to_string();
                if pinned_fp == peer_fingerprint {
                    result = true; // Exact match
                } else if published_fingerprints.contains(&peer_fingerprint)
                    && published_fingerprints.contains(&pinned_fp)
                {
                    // D-09: Both fingerprints in published array = cert rotation
                    table.insert(server_id, peer_fingerprint).map_err(|e| e.to_string())?;
                    tracing::info!(
                        "[tofu] Cert rotation for {}: {} -> {}",
                        server_id, pinned_fp, peer_fingerprint
                    );
                    result = true;
                } else {
                    tracing::warn!(
                        "[tofu] MISMATCH for {}: pinned={}, peer={}",
                        server_id, pinned_fp, peer_fingerprint
                    );
                    result = false;
                }
            }
        }
    }
    write_txn.commit().map_err(|e| e.to_string())?;
    Ok(result)
}
```

## State of the Art

## Open Questions

1. **Thread message storage format and indexing**
   - What we know: Origin server must store messages for backfill (BKFL-01). redb provides the storage engine. Key format `{thread_id}:{sequence_number}` works for cursor-based pagination.
   - What's unclear: How much memory/disk this consumes for the demo. Whether thread messages should have their own retention policy.
   - Recommendation: Store messages in redb with thread_id:sequence composite key. No retention policy for demo (threads are short-lived). Document that production would need pruning.

2. **redb file location in Docker**
   - What we know: Docker containers need persistent volumes for redb files to survive restarts (DEMO-03).
   - What's unclear: Best path convention inside the container.
   - Recommendation: Use `/data/ainm.redb` as the default path, mount as a named Docker volume.

3. **Relay params signing scope with new fields**
   - What we know: `sign_relay_params` signs the entire params object. Adding `relay_timestamp` and `relay_id` means they are automatically included in the signature -- good, prevents tampering.
   - What's unclear: Whether relay_id should be excluded from signing (like `server_signature` is).
   - Recommendation: Include relay_timestamp and relay_id in the signed payload. They are integral to the relay and should be tamper-proof. Only `server_signature` itself is excluded.
