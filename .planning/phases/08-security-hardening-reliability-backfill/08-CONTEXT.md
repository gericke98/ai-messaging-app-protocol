<decisions>
## Implementation Decisions

### Replay Protection
- **D-01:** 5-minute replay rejection window. Relay payloads older than 5 minutes are rejected. Tolerates minor clock drift between servers.
- **D-02:** `relay_id` is a UUIDv7 generated by the sender per relay payload. Time-ordered for efficient dedup cache cleanup.
- **D-03:** `relay_timestamp` (RFC 3339) + `relay_id` (UUIDv7) added to relay params. Receiver checks timestamp freshness (5-min window) and dedup cache (reject duplicate relay_id within window).
- **D-04:** Dedup cache and TOFU pin store both persisted in redb. Survives server restarts — prevents replay attacks and TOFU bypass after reboot.

### TOFU Key Pinning
- **D-05:** SSH-style Trust On First Use. First contact with a remote server pins its TLS fingerprint. Future connections must match the pinned fingerprint or be rejected. Warning logged on mismatch.
- **D-06:** TOFU pins stored in redb (same engine as offline queue and dedup cache). One storage engine for all Phase 8 persistence.

### Certificate Rotation
- **D-07:** Replace singular `tls_fingerprint` with `tls_fingerprints` array in `.well-known/ainm/server`. Max 2 entries: [current, previous]. Single-entry array for non-rotating servers.
- **D-08:** Clean break from Phase 7's singular field — no backwards compatibility shim needed (Phase 7 was demo-only, no deployed servers).
- **D-09:** TOFU auto-update on rotation: when a server presents a new fingerprint that appears in `tls_fingerprints` alongside a currently pinned one, automatically update the pin to the new fingerprint. Known fingerprint vouches for the new one. Log the rotation event.

### Persistent Offline Queue
- **D-10:** redb replaces in-memory `VecDeque` in `relay.rs`. Per-destination persistent queues that survive server restarts.
- **D-11:** Count-based queue bound: 10,000 messages per destination. Oldest messages evicted when full (FIFO). Warning logged with count of dropped messages.
- **D-12:** 7-day retention policy enforced by hourly background cleanup task scanning redb. UUIDv7 keys are time-ordered, making age-based cleanup efficient.
- **D-13:** Sender gets success on enqueue — relay delivery is best-effort. Queue full = drop oldest, not backpressure.

### Partition Healing
- **D-14:** When connectivity is restored to a previously unreachable server, drain the persistent queue FIFO. Reset backoff on reconnection. Messages arrive in queued order.
- **D-15:** No automatic backfill request on reconnection (keeps queue and backfill features decoupled). Backfill is on-demand only.

### Backfill Endpoint
- **D-16:** `ainm.backfill` JSON-RPC method on the existing `/ainm/v1/relay` POST endpoint. Same mTLS authentication. No new federation endpoint.
- **D-17:** Cursor-based pagination using thread sequence numbers. Params: `thread_id`, `after_sequence` (cursor), `limit` (default 50, max 200). Response: `messages` array + `has_more` boolean + `next_cursor`.
- **D-18:** Authorization via ThreadRegistry — requesting server must have at least one participant in the thread's `participating_servers` set. Already tracked in `federation.rs`.
- **D-19:** Post-join visibility only. Backfill returns only messages after the requesting server's earliest participant joined the thread. No pre-join access option in this phase (defer to v2).

### Claude's Discretion
- redb table/key design for offline queue, dedup cache, and TOFU pin store
- Exact cleanup task scheduling mechanism (tokio interval vs dedicated task)
- Internal module organization for new persistence layer
- Spec prose wording for new transport.md sections (backfill, replay protection, tls_fingerprints)
- Demo scenario scripts for DEMO-03 and DEMO-04

</decisions>

<specifics>
## Specific Ideas

- redb is a single-file embedded database (like SQLite but pure Rust, ACID). One `.redb` file stores offline queue, dedup cache, and TOFU pins in separate tables.
- The dedup cache cleanup can piggyback on the same hourly retention cleanup task — scan both redb tables in one pass.
- For DEMO-03 (partition healing): docker-compose stop server-b, send messages from server-a, docker-compose start server-b, verify messages arrive.
- For DEMO-04 (cert rotation): generate new cert for server-b, update .well-known with [new, old] fingerprints, restart server-b with new cert, verify federation continues and TOFU pin auto-updates.

</specifics>
