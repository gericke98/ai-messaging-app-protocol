Write `spec/content.md` following the spec document internal structure pattern from research.

**Document structure:**

### 1. Overview (2-3 paragraphs)
- Content blocks are the atomic units of message content in AINM
- Messages contain an array of typed content blocks (D-09), enabling rich multi-part messages
- Extensibility model: closed core set + namespaced extensions (D-13) with mandatory fallback (D-14)

### 2. Terminology
Define: content block, block type, core block, extension block, fallback, source, version

### 3. Content Block Base Schema (CONT-01)
Every content block shares these fields:
```json
{
  "type": "<block-type-identifier>",
  "version": "1.0",
  "source": "user" | "agent" | "system",
  "fallback": "<plain-text-or-markdown-fallback>"
}
```
- `type` (string, REQUIRED): Block type identifier. Core types are bare strings (e.g., `"text"`). Extension types use reverse-domain namespacing (e.g., `"com.example.weather-card"`) (D-13)
- `version` (string, REQUIRED): Semantic version of the block type schema. Clients check this to determine which fields to expect (D-15). Format: `"MAJOR.MINOR"` -- MAJOR changes break backward compatibility, MINOR adds optional fields
- `source` (string, REQUIRED): Trust annotation -- `"user"`, `"agent"`, or `"system"` (D-10). See security.md for full semantics
- `fallback` (string, REQUIRED): Plain text or markdown representation of the block's content (D-14). Clients MUST render this when they do not recognize the block type or version. Guarantees graceful degradation

### 4. Core Block Types (CONT-02)

#### 4.1 TextBlock
```json
{
  "type": "text",
  "version": "1.0",
  "source": "user",
  "text": "Hello, can you help me with this code?\n\nI'm getting a **weird error** on line 42.",
  "mentions": [
    {
      "address": "code-bot@agents.example.com",
      "offset": 4,
      "length": 33
    }
  ],
  "fallback": "Hello, can you help me with this code? I'm getting a weird error on line 42."
}
```
- `text` (string, REQUIRED): Markdown-formatted text content. Supports CommonMark syntax
- `mentions` (array, OPTIONAL): Array of mention annotations referencing participant addresses. Each mention has:
  - `address` (string, REQUIRED): Full AINM address of the mentioned participant
  - `offset` (integer, REQUIRED): Zero-based character offset in `text` where the mention display text begins
  - `length` (integer, REQUIRED): Length of the mention display text in characters
- Mentions enable @-mention functionality across participant types (MIXD-04 -- specified here for completeness, normatively defined in threading.md)

#### 4.2 CodeBlock
```json
{
  "type": "code",
  "version": "1.0",
  "source": "agent",
  "language": "python",
  "code": "def fibonacci(n):\n    if n <= 1:\n        return n\n    return fibonacci(n-1) + fibonacci(n-2)",
  "filename": "fibonacci.py",
  "fallback": "```python\ndef fibonacci(n):\n    if n <= 1:\n        return n\n    return fibonacci(n-1) + fibonacci(n-2)\n```"
}
```
- `language` (string, REQUIRED): Programming language identifier. Use common identifiers: `python`, `javascript`, `typescript`, `rust`, `swift`, `json`, `yaml`, `markdown`, `bash`, `sql`, etc.
- `code` (string, REQUIRED): Source code content (raw, no markdown wrapping)
- `filename` (string, OPTIONAL): Suggested filename for the code

#### 4.3 ImageBlock
```json
{
  "type": "image",
  "version": "1.0",
  "source": "user",
  "url": "https://cdn.example.com/images/screenshot.png",
  "mime_type": "image/png",
  "alt": "Screenshot showing the error dialog",
  "width": 1920,
  "height": 1080,
  "size_bytes": 245760,
  "fallback": "[Image: Screenshot showing the error dialog]"
}
```
- `url` (string, REQUIRED): HTTPS URL to the image. HTTP URLs MUST be rejected
- `mime_type` (string, REQUIRED): IANA media type (e.g., `image/png`, `image/jpeg`, `image/webp`, `image/gif`)
- `alt` (string, REQUIRED): Alternative text description for accessibility
- `width` (integer, OPTIONAL): Image width in pixels
- `height` (integer, OPTIONAL): Image height in pixels
- `size_bytes` (integer, OPTIONAL): File size in bytes

#### 4.4 FileBlock
```json
{
  "type": "file",
  "version": "1.0",
  "source": "user",
  "url": "https://cdn.example.com/files/report.pdf",
  "mime_type": "application/pdf",
  "filename": "quarterly-report.pdf",
  "size_bytes": 1048576,
  "digest": "sha256:b94d27b9934d3e08a52e52d7da7dabfac484efe37a5380ee9088f7ace2efcde9",
  "fallback": "[File: quarterly-report.pdf (1.0 MB, PDF)]"
}
```
- `url` (string, REQUIRED): HTTPS URL to the file. HTTP URLs MUST be rejected
- `mime_type` (string, REQUIRED): IANA media type
- `filename` (string, REQUIRED): Original filename for display and download
- `size_bytes` (integer, REQUIRED): File size in bytes
- `digest` (string, REQUIRED): Content hash in format `algorithm:hex-encoded-hash`. Algorithm MUST be `sha256`. Enables integrity verification independent of transport

### 5. Extension Block Types (D-13)
- Extension types use reverse-domain namespacing: `com.example.custom-chart`, `io.mycompany.approval-form`
- Clients MUST render core block types. Clients MAY render extension block types. Clients that do not recognize an extension type MUST render the `fallback` field
- Extension blocks may include any additional fields beyond the base schema
- Example:
```json
{
  "type": "com.example.weather-card",
  "version": "1.0",
  "source": "agent",
  "data": {
    "city": "Madrid",
    "temperature": 22,
    "unit": "celsius",
    "condition": "sunny"
  },
  "fallback": "Madrid: 22C, Sunny"
}
```
- Namespace registration: this protocol does not define a namespace registry. Implementers SHOULD use domains they control. Collisions between different implementers using the same namespace are resolved by the client's extension rendering logic

### 6. Content Block Ordering
- Content blocks are ordered: the `content` array preserves insertion order
- Clients SHOULD render blocks in array order (top to bottom)
- A single message MAY contain multiple blocks of different types (e.g., a text explanation followed by a code block)
- A single message MAY contain multiple blocks of the same type

### 7. Error Handling
- Missing required fields: implementations MUST reject content blocks with missing required fields and return JSON-RPC error `-32013` (Malformed message)
- Unknown core block version: if `version` major is higher than supported, render `fallback`
- Empty content array: allowed for non-message types (e.g., `thread.join`). For `type: "message"`, content array MUST contain at least one block

### 8. Security Considerations
- URL validation: all `url` fields in ImageBlock and FileBlock MUST use HTTPS
- Content hash verification: FileBlock `digest` enables clients to verify downloaded file integrity
- Fallback spoofing: the `fallback` field could misrepresent the actual block content. Clients rendering the actual block type SHOULD NOT also display the fallback

### 9. Examples
- Simple text-only message (1 TextBlock)
- Rich agent response (TextBlock + CodeBlock)
- File sharing (TextBlock + FileBlock)
- Extension block with fallback rendering

Write `spec/transport.md` following the spec document internal structure pattern from research.

**Document structure:**

### 1. Overview (2-3 paragraphs)
- Transport defines how messages move between participants via servers
- Two bindings: WebSocket (client-to-server, real-time) and HTTP (server-to-server, federation relay)
- All transport uses JSON-RPC 2.0 framing over TLS 1.3

### 2. Terminology
Define: transport binding, client, server, connection, session, handshake, capability negotiation, streaming mode, store-and-forward mode, notification, request, response

### 3. JSON-RPC 2.0 Framing (TRNS-04)
All protocol messages use JSON-RPC 2.0 envelope:

**Request:**
```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "ainm.message.send",
  "params": { ... }
}
```

**Response (success):**
```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": { ... }
}
```

**Response (error):**
```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32010,
    "message": "Invalid signature",
    "data": { "field": "signature" }
  }
}
```

**Notification (no response expected):**
```json
{
  "jsonrpc": "2.0",
  "method": "ainm.message.deliver",
  "params": { ... }
}
```

- Method namespace: all AINM methods use `ainm.` prefix
- Standard JSON-RPC error codes apply: `-32700` (Parse error), `-32600` (Invalid Request), `-32601` (Method not found), `-32602` (Invalid params), `-32603` (Internal error)
- Protocol-specific error codes: `-32010` through `-32019` (security errors, defined in security.md), `-32020` through `-32029` (transport errors), `-32030` through `-32039` (thread errors)
- Batch requests: JSON-RPC 2.0 batch format (array of requests) is supported but OPTIONAL for implementations

### 4. WebSocket Transport Binding (TRNS-01)

#### 4.1 Connection Establishment
- URL pattern: `wss://{server}/ainm/v1` (the `server` field from identity resolution)
- TLS 1.3 REQUIRED (TRNS-03). Connections over `ws://` (unencrypted) MUST be rejected
- Standard WebSocket upgrade handshake (RFC 6455)

#### 4.2 Connection Lifecycle (modeled on MCP)

```
Client                          Server
  |                               |
  |--- WebSocket upgrade -------->|  (TLS 1.3 required)
  |<-- 101 Switching Protocols ---|
  |                               |
  |--- ainm.initialize ---------->|  JSON-RPC request
  |<-- result: capabilities ------|  JSON-RPC response
  |--- ainm.initialized --------->|  JSON-RPC notification
  |                               |
  |  [Normal operation phase]     |
  |--- ainm.message.send -------->|  Client sends message
  |<-- ainm.message.deliver ------|  Server delivers message (notification)
  |                               |
  |--- ainm.ping ---------------->|  Keepalive (request)
  |<-- ainm.pong -----------------|  Keepalive (response)
  |                               |
  |--- close frame / ainm.shutdown|  Graceful shutdown
  |<-- close frame ---------------|
```

#### 4.3 Initialize (ainm.initialize)
**Request:**
```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "ainm.initialize",
  "params": {
    "protocolVersion": "0.1.0",
    "identity": "alice@messaging.example.com",
    "signature": "<base64url-signature-of-initialization-nonce>",
    "capabilities": {
      "streaming": true,
      "subThreads": true,
      "contentTypes": ["text", "code", "image", "file"]
    }
  }
}
```
**Response:**
```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "0.1.0",
    "serverInfo": {
      "name": "messaging.example.com",
      "version": "0.1.0"
    },
    "capabilities": {
      "streaming": true,
      "subThreads": true,
      "storeAndForward": true,
      "maxContentBlocks": 50,
      "maxMessageSize": 1048576
    },
    "nonce": "<server-generated-nonce-for-client-auth>"
  }
}
```
**Confirmation notification:**
```json
{
  "jsonrpc": "2.0",
  "method": "ainm.initialized"
}
```
- Client MUST send `ainm.initialize` as the first message after WebSocket connection
- Server MUST NOT process any other method until initialization is complete
- Version negotiation: client sends its supported version, server responds with the version it will use. If incompatible, server returns error `-32020` (Unsupported protocol version) and closes the connection
- Capability exchange: client and server declare their capabilities. Features not declared by both sides are unavailable for the session

#### 4.4 Protocol Methods
Define each JSON-RPC method with request/response schemas:

**ainm.message.send** (client -> server, request):
- `params`: The signed message envelope (as defined in security.md)
- `result`: `{ "accepted": true, "server_timestamp": "2026-03-28T12:34:57.000Z" }`
- Server validates signature, checks thread membership, queues for delivery

**ainm.message.deliver** (server -> client, notification):
- `params`: The signed message envelope
- Delivered to all clients connected to threads the message targets
- No response expected (notification pattern)

**ainm.thread.create** (client -> server, request):
- `params`: `{ "thread_id": "UUIDv7", "parent_thread_id": "UUIDv7 (optional)", "parent_message_id": "UUIDv7 (optional)", "title": "string (optional)", "participants": ["address1", "address2"] }`
- `result`: `{ "thread_id": "UUIDv7", "created_at": "RFC3339" }`

**ainm.thread.join** (client -> server, request):
- `params`: `{ "thread_id": "UUIDv7", "identity": "address" }`
- `result`: `{ "joined": true }`

**ainm.thread.leave** (client -> server, request):
- `params`: `{ "thread_id": "UUIDv7", "identity": "address" }`
- `result`: `{ "left": true }`

**ainm.presence.update** (client -> server, notification):
- `params`: `{ "identity": "address", "status": "online|offline|away|dnd|available|busy|processing", "thread_id": "UUIDv7 (optional)", "detail": "string (optional)" }`

**ainm.presence.notify** (server -> client, notification):
- `params`: Same structure as presence.update, broadcast to thread participants

**ainm.ping** / **ainm.pong** (keepalive):
- `ainm.ping` (request): `{ }` (empty params)
- `ainm.pong` (response): `{ "timestamp": "RFC3339" }`
- Clients SHOULD send ping every 30 seconds. Server MUST respond within 10 seconds or client SHOULD reconnect

**ainm.shutdown** (client -> server, notification):
- `params`: `{ "reason": "string (optional)" }`
- Graceful disconnection. Server clears session state and marks participant as offline

#### 4.5 Reconnection
- Clients SHOULD implement exponential backoff for reconnection: 1s, 2s, 4s, 8s, ... up to 60s maximum
- After reconnection, client MUST re-initialize (`ainm.initialize`)
- Server delivers any queued messages (store-and-forward) after re-initialization

### 5. HTTP Transport Binding (TRNS-02)

#### 5.1 Server-to-Server Relay
- Used for federated message delivery between servers
- Endpoint: `POST https://{target-server}/ainm/v1/relay`
- Mutual TLS (mTLS) required: both servers present TLS certificates
- Server discovery: resolve the target participant's identity -> `server` field indicates their home server

#### 5.2 Server Identity
- Servers publish their identity at `GET https://{domain}/.well-known/ainm/server`
```json
{
  "server_id": "messaging.example.com",
  "public_key": "<base64url-Ed25519-public-key>",
  "relay_endpoint": "https://messaging.example.com/ainm/v1/relay",
  "tls_fingerprint": "sha256:<hex-encoded-certificate-fingerprint>",
  "supported_versions": ["0.1.0"]
}
```

#### 5.3 Relay Request
```json
POST /ainm/v1/relay HTTP/1.1
Host: messaging.example.com
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "ainm.relay",
  "params": {
    "messages": [
      { ... signed message envelope ... }
    ],
    "from_server": "agents.example.com",
    "server_signature": "<base64url-signature-of-relay-payload-by-originating-server>"
  }
}
```
**Response:**
```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "accepted": 1,
    "rejected": 0,
    "errors": []
  }
}
```
- Originating server signs the relay payload with its own Ed25519 key (server-level signing)
- Receiving server validates: (1) mTLS certificate matches `tls_fingerprint` from server identity, (2) server_signature is valid, (3) each individual message signature is valid

### 6. Delivery Modes (TRNS-05)

#### 6.1 Streaming Mode (Foreground)
- Default for connected clients
- Messages delivered immediately via WebSocket notifications (`ainm.message.deliver`)
- Real-time: server pushes messages as they arrive
- Used when client is connected and has completed initialization

#### 6.2 Store-and-Forward Mode (Background/Offline)
- Activated when a recipient is not connected (no active WebSocket session)
- Server queues messages for later delivery
- On reconnection, server delivers queued messages in chronological order after `ainm.initialized`
- Queue semantics:
  - Servers SHOULD retain messages for at least 7 days
  - Servers MAY communicate their retention policy during capability exchange
  - Messages are delivered in `timestamp` order
  - At-least-once delivery: clients handle deduplication via message `id` (see security.md)

### 7. Error Handling
Transport-specific error codes:
- `-32020`: Unsupported protocol version (initialization failure)
- `-32021`: Not initialized (method called before initialization complete)
- `-32022`: Rate limited (too many requests)
- `-32023`: Server unavailable (relay target unreachable)
- `-32024`: Thread not found
- `-32025`: Not a thread participant (unauthorized)

### 8. Security Considerations
- TLS 1.3 is REQUIRED for both WebSocket and HTTP bindings (TRNS-03). No fallback to older TLS versions
- Server-to-server relay uses mTLS for bidirectional authentication
- Rate limiting: servers SHOULD implement rate limiting per client session and per relay source
- Connection hijacking: the initialization handshake with identity + signature prevents unauthorized connections

### 9. Examples
- Full WebSocket session: connect -> initialize -> send message -> receive message -> shutdown
- Server-to-server relay: Alice on server A sends to Bob on server B
- Reconnection with queued message delivery
