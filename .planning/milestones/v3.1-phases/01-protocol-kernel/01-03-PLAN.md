**Document structure:**

### 1. Overview (2-3 paragraphs)
- Threads are the organizational unit of conversation in AINM
- Design philosophy: flat by default, one level of sub-threading, mixed human-agent participation as equals
- This spec builds on identity.md (participants), security.md (message signing), content.md (message content), and transport.md (delivery methods)

### 2. Terminology
Define: thread, root thread, sub-thread, participant, thread creator, parent thread, parent message, context inheritance, presence, mention

### 3. Thread Model (THRD-01)
- A thread is a chronologically-ordered stream of messages identified by a `thread_id` (UUIDv7)
- Conversations are flat by default: messages within a thread form a single, chronological sequence
- Thread-addressed delivery (D-11): messages are sent TO a `thread_id`, not to individual participants. All thread members receive all messages
- DMs are threads with exactly 2 participants -- no special-casing at the protocol level
- Thread metadata:
```json
{
  "thread_id": "019580a0-1234-7000-8000-000000000001",
  "title": "Project discussion",
  "created_at": "2026-03-28T12:00:00.000Z",
  "created_by": "alice@messaging.example.com",
  "parent_thread_id": null,
  "parent_message_id": null,
  "participants": [
    {
      "identity": "alice@messaging.example.com",
      "type": "human",
      "joined_at": "2026-03-28T12:00:00.000Z",
      "role": "creator"
    },
    {
      "identity": "code-bot@agents.example.com",
      "type": "agent",
      "joined_at": "2026-03-28T12:00:05.000Z",
      "role": "member"
    }
  ]
}
```
- Participant roles: `"creator"` (the thread creator, one per thread) and `"member"` (all other participants). Both have equal messaging capabilities -- role is informational only.
- Thread creation uses `ainm.thread.create` (defined in transport.md):
```json
{
  "jsonrpc": "2.0",
  "id": 42,
  "method": "ainm.thread.create",
  "params": {
    "thread_id": "019580a0-1234-7000-8000-000000000001",
    "title": "Project discussion",
    "participants": [
      "alice@messaging.example.com",
      "code-bot@agents.example.com"
    ]
  }
}
```
- The creator generates the `thread_id` (UUIDv7) client-side. Server validates uniqueness.

### 4. Sub-Threading (THRD-02, THRD-04)
- Any participant (human or agent) can create a sub-thread from any message in a parent thread
- Sub-threads are ONE level of nesting only. Creating a sub-thread within a sub-thread is NOT allowed. Implementations MUST reject `ainm.thread.create` with a `parent_thread_id` that is itself a sub-thread (return error `-32030`: "Nested sub-threads not allowed")
- Sub-thread creation references both the parent thread and the specific message:
```json
{
  "jsonrpc": "2.0",
  "id": 43,
  "method": "ainm.thread.create",
  "params": {
    "thread_id": "019580a3-5678-7000-8000-111111111111",
    "parent_thread_id": "019580a0-1234-7000-8000-000000000001",
    "parent_message_id": "019580a1-7b3e-7000-8000-abcdef123456",
    "title": "Debugging the weather API call",
    "participants": [
      "alice@messaging.example.com",
      "weather-bot@agents.example.com"
    ]
  }
}
```
- `parent_thread_id` (string, OPTIONAL): UUIDv7 of the parent thread. Present only for sub-threads.
- `parent_message_id` (string, OPTIONAL): UUIDv7 of the message the sub-thread branches from. Present only for sub-threads.
- Agents creating sub-threads (THRD-04): agents use the same `ainm.thread.create` mechanism. Common use case: agent-to-agent side conversations (e.g., a coding agent spawns a sub-thread to consult a testing agent, then reports results back to the parent thread).
- Agent sub-thread example:
```json
{
  "jsonrpc": "2.0",
  "id": 44,
  "method": "ainm.thread.create",
  "params": {
    "thread_id": "019580a4-9abc-7000-8000-222222222222",
    "parent_thread_id": "019580a0-1234-7000-8000-000000000001",
    "parent_message_id": "019580a2-9c4f-7000-8000-fedcba987654",
    "title": "Agent coordination: test coverage analysis",
    "participants": [
      "code-bot@agents.example.com",
      "test-bot@agents.example.com"
    ]
  }
}
```

### 5. Context Inheritance (THRD-03)
Define precisely what "context" a sub-thread inherits from its parent:

**Inherited:**
- Participant list: sub-thread creator specifies initial participants, but they MUST be a subset of the parent thread's participants (or new participants explicitly invited). The sub-thread does NOT automatically include all parent participants -- the creator chooses.
- Thread metadata: sub-thread has access to `parent_thread_id` and `parent_message_id`, allowing implementations to show the branching point
- Security context: sub-thread messages are signed with the same identity keys

**NOT inherited (explicitly):**
- Messages: parent thread messages are NOT automatically forwarded to the sub-thread. The sub-thread is a fresh conversation starting from the context of the parent message
- Presence: presence is per-thread. A participant's presence in the parent thread does not affect their presence in the sub-thread

**Rationale:** Minimal inheritance keeps the model simple and prevents the complexity explosion Matrix experienced with threading (Pitfall 4 from research). Participants who need parent thread context can reference the `parent_message_id`.

### 6. Participant Management
- **Joining:** `ainm.thread.join` (defined in transport.md). Any current participant can invite another participant by sending `ainm.thread.join` on their behalf. The invited participant's server receives a notification.
- **Leaving:** `ainm.thread.leave` (defined in transport.md). Any participant can leave a thread at any time. Leaving generates a system message visible to remaining participants:
```json
{
  "id": "019580a5-def0-7000-8000-333333333333",
  "from": "system@messaging.example.com",
  "thread_id": "019580a0-1234-7000-8000-000000000001",
  "timestamp": "2026-03-28T13:00:00.000Z",
  "type": "thread.leave",
  "content": [
    {
      "type": "text",
      "version": "1.0",
      "source": "system",
      "text": "alice@messaging.example.com has left the thread.",
      "fallback": "alice@messaging.example.com has left the thread."
    }
  ],
  "signature": "<server-signature>"
}
```
- Thread deletion: threads are not explicitly deleted. A thread with zero participants is considered inactive. Servers MAY garbage-collect inactive threads after a retention period.

### 7. Mixed Thread Participation (MIXD-01, MIXD-02)
- Threads support any combination of human and agent participants as equals (MIXD-01)
- The participant interface is uniform regardless of type (MIXD-02):
  - Same address format (`name@provider`)
  - Same message envelope (id, from, thread_id, timestamp, type, content, signature)
  - Same content blocks (text, code, image, file)
  - Same thread operations (create, join, leave)
- No type-specific message fields. The ONLY place participant type is visible is:
  1. The `type` field in identity resolution response (identity.md)
  2. The `source` field in content blocks (security.md) -- `"user"` vs `"agent"` vs `"system"`
  3. The presence states available (see section 8)

Example: mixed thread with 2 humans and 1 agent:
```json
{
  "thread_id": "019580a0-1234-7000-8000-000000000001",
  "title": "Code review with AI assistance",
  "participants": [
    { "identity": "alice@messaging.example.com", "type": "human", "role": "creator" },
    { "identity": "bob@messaging.example.com", "type": "human", "role": "member" },
    { "identity": "code-bot@agents.example.com", "type": "agent", "role": "member" }
  ]
}
```

### 8. Presence Semantics (MIXD-03)
Adapted from RFC 2778 presence model. Presence is thread-scoped: a participant has a separate presence state per thread.

**Human presence states:**
- `online`: Actively connected, viewing the thread
- `offline`: Not connected
- `away`: Connected but inactive (idle timeout, implementation-defined)
- `dnd` (do not disturb): Connected but should not be notified

**Agent presence states:**
- `available`: Agent is connected and ready to process messages
- `busy`: Agent is connected but handling capacity is limited
- `processing`: Agent is actively generating a response (typing indicator equivalent)
- `offline`: Agent is not connected or not accepting messages

**Presence updates** use `ainm.presence.update` and `ainm.presence.notify` (defined in transport.md):
```json
{
  "jsonrpc": "2.0",
  "method": "ainm.presence.update",
  "params": {
    "identity": "code-bot@agents.example.com",
    "status": "processing",
    "thread_id": "019580a0-1234-7000-8000-000000000001",
    "detail": "Analyzing code for potential bugs"
  }
}
```
- `status` (string, REQUIRED): One of the valid states for the participant's type
- `thread_id` (string, OPTIONAL): If present, the presence applies to this specific thread. If absent, applies globally to all threads
- `detail` (string, OPTIONAL): Human-readable description of what the participant is doing. Particularly useful for agent `processing` state

**Type validation:** Servers SHOULD validate that the presence status is valid for the participant's type (resolved from identity). A human sending `status: "processing"` is invalid. Server MAY reject with error `-32031` (Invalid presence state for participant type) or silently map to the closest valid state.

### 9. @-Mentions (MIXD-04)
- Mentions are a content-level feature defined in content.md's TextBlock `mentions` array
- Mentions work uniformly across participant types: humans can @-mention agents and vice versa
- A mention is an annotation within a text block that references a participant's AINM address:
```json
{
  "type": "text",
  "version": "1.0",
  "source": "user",
  "text": "Hey @code-bot, can you review this? @bob what do you think?",
  "mentions": [
    { "address": "code-bot@agents.example.com", "offset": 4, "length": 9 },
    { "address": "bob@messaging.example.com", "offset": 42, "length": 4 }
  ],
  "fallback": "Hey @code-bot, can you review this? @bob what do you think?"
}
```
- **Mention behavior:**
  - When a participant is @-mentioned, the server SHOULD deliver a notification to that participant even if they have `dnd`/`away` status (implementation-defined)
  - Agents receiving a mention SHOULD treat it as a direct invocation and respond
  - The display text in the `text` field (e.g., `@code-bot`) is a shorthand. The `mentions` array provides the canonical address for resolution
  - Mentions of participants not in the thread are allowed but servers MAY warn the sender

### 10. Security Considerations
- Thread access control: only thread participants can send messages to a thread. Servers MUST reject `ainm.message.send` from non-participants with error `-32025` (Not a thread participant)
- Sub-thread access: sub-thread participants are explicitly specified at creation time and do not automatically include all parent thread participants. This prevents information leakage
- System messages: join/leave/system notifications have `source: "system"`. Participants SHOULD verify that system messages come from a trusted server address
- Agent impersonation: since participant type is in identity metadata (not the message), an agent cannot claim to be human. The `source` field further distinguishes content origin

### 11. Examples
- Complete thread lifecycle: create thread -> add participants -> exchange messages -> create sub-thread -> leave thread
- Agent-to-agent sub-thread: agent spawns coordination thread, consults another agent, reports back
- Mixed thread with @-mentions: human mentions agent, agent responds with code block
- Presence flow: agent joins thread as `available`, transitions to `processing` while generating response, back to `available`
