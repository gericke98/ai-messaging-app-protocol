Create `spec/compatibility.md` following the Phase 1 spec document template.

The specification MUST cover these sections:

**Section 1: Overview** -- AINM provides compatibility bridges to two major ecosystem protocols: MCP (Model Context Protocol) for tool integration, and A2A (Agent-to-Agent) for agent interoperability. These bridges enable existing MCP servers to be exposed as AINM thread participants, and A2A task lifecycle to be represented as AINM thread events. Bridges are implemented as proxy participants -- AINM server components with their own identities that translate between protocols.

**Section 2: Terminology** -- Define: bridge, proxy participant, MCP bridge, A2A bridge, tool mapping, task mapping, bridge identity.

**Section 3: MCP Bridge**

**3.1 Architecture** -- The MCP bridge is a proxy participant: an AINM server component that (1) connects to an MCP server as an MCP client, (2) registers as an AINM participant with its own identity (e.g., `mcp-{server-name}@{provider}`), (3) publishes an Agent Card with the MCP server's tools in `ainm.tools`, and (4) translates between AINM thread messages and MCP tool calls.

**3.2 Tool Discovery Mapping**
- MCP `tools/list` response -> Agent Card `ainm.tools` array
- Each MCP tool's `name`, `description`, `inputSchema` maps directly to the corresponding Agent Card tool fields
- MCP `notifications/tools/list_changed` -> Agent Card ETag update (client refetches card)
- Tool names are preserved verbatim from MCP

**3.3 Tool Invocation Mapping**
When a thread participant requests a tool call from the MCP bridge:
1. Bridge receives request (e.g., via @-mention with tool name)
2. Bridge sends `tool.call.started` event to the thread (per tool-visibility.md)
3. Bridge calls MCP `tools/call` with the tool name and input parameters
4. If MCP supports streaming results, bridge sends `tool.call.progress` events
5. On MCP tool result, bridge sends `tool.call.completed` event to the thread
6. Bridge MAY also send a regular message with the full tool result as content blocks

**3.4 Error Mapping**
- MCP error responses map to `tool.call.completed` with `status: "error"`
- MCP connection failures result in a system message to the thread
- MCP tool timeout maps to `tool.call.completed` with `status: "error"` and appropriate error_message

**3.5 Limitations**
- MCP resources (read-only data) are not directly mapped in v1 -- agents must use tools to access them
- MCP prompts are not mapped -- AINM has its own context management via memory spec
- The bridge operates as a single participant; multiple MCP servers require multiple bridge instances

**Section 4: A2A Bridge**

**4.1 Architecture** -- The A2A bridge maps A2A task lifecycle to AINM thread events. It can operate in two modes: (1) **outbound** -- an AINM participant delegates work to an external A2A agent, the bridge translates AINM messages to A2A task operations; (2) **inbound** -- an external A2A agent sends tasks that appear as AINM thread events. The bridge has its own AINM identity.

**4.2 Task Lifecycle Mapping**

| A2A Task State | AINM Equivalent | How |
|----------------|-----------------|-----|
| submitted | `ainm.thread.create` (sub-thread) or new message | Bridge creates a sub-thread for the task with task metadata |
| working | `ainm.presence.update` status: "processing" | Bridge updates presence to processing with task detail |
| input-required | Message with FormBlock or ApprovalBlock | Bridge sends interactive content requesting user input |
| completed | Message with result content blocks | Bridge delivers result as TextBlock, CodeBlock, etc. |
| failed | Message with error description | Bridge sends error as TextBlock with source: "system" |
| canceled | Thread leave or stream cancel | Bridge leaves sub-thread or cancels active stream |

**4.3 Agent Card Compatibility** -- Per D-09 and agent-card.md, AINM Agent Cards are a superset of A2A Agent Cards. An A2A client can discover an AINM agent by reading the top-level A2A fields. An AINM client can discover A2A agents if their Agent Cards are accessible at a well-known URL. The bridge can translate between the two card formats by extracting the A2A-compatible subset from an AINM Agent Card, or by wrapping an A2A card with AINM extension fields.

**4.4 Artifact Mapping** -- A2A task artifacts (files produced by the task) map to FileBlock content in the AINM result message. The bridge downloads artifacts from the A2A artifact URL and delivers them as FileBlocks with appropriate MIME types.

**4.5 Limitations**
- A2A push notifications are not mapped to AINM in v1 (AINM uses WebSocket for real-time)
- A2A multi-turn tasks work naturally via the sub-thread model -- each input-required state maps to an interactive block in the sub-thread
- A2A streaming (SSE-based) maps to AINM streaming if the A2A agent supports it

**Section 5: Bridge Identity and Security**
- Bridges register as AINM participants with their own identities
- Bridge identities SHOULD include a naming convention indicating they are bridges: `mcp-{name}@provider` or `a2a-{name}@provider`
- Bridge messages are signed with the bridge's Ed25519 key
- The `source` field on content blocks from bridges is `"agent"` (the bridge acts on behalf of the external service)
- Bridge Agent Cards SHOULD include a field in the `ainm` extension indicating the bridge type and the external service

**Section 6: Error Handling** -- Bridge-specific error scenarios are handled via thread messages (system type) and tool events (error status). No new error code range -- bridges use existing transport and tool error codes. Protocol-level errors (malformed bridge config, external service unreachable) result in system messages to the thread.

**Section 7: Security Considerations** -- Bridges are trust boundaries. An AINM server that operates a bridge trusts the external MCP/A2A service. Participants in a thread see bridge actions but cannot directly access the external service. Bridge identities are distinct from the external service identities. Servers SHOULD require explicit configuration to enable bridges (not auto-discovered). MCP tool inputs may contain sensitive data -- the bridge MUST follow the same input visibility rules as tool-visibility.md.

**Section 8: Examples** -- (1) MCP bridge example: user @-mentions MCP bridge, bridge calls code_search tool, delivers results. (2) A2A bridge example: user delegates task to external A2A agent, task goes through submitted -> working -> completed lifecycle in a sub-thread.
