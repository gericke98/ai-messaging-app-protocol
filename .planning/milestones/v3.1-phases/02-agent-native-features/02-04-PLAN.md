Create `spec/memory.md` following the Phase 1 spec document template.

The specification MUST cover these sections:

**Section 1: Overview** -- Memory management enables structured context delivery to agents instead of raw message dumps. AINM defines three memory tiers inspired by Letta/MemGPT, adapted for a multi-participant protocol: active context (always in the agent's working memory), conversation memory (full thread history, queryable), and archival memory (cross-conversation persistent knowledge). The server is authoritative for all memory management (per D-13). Participants can request operations; the server enforces policy.

**Section 2: Terminology** -- Define: memory tier, active context, conversation memory, archival memory, context frame, fact, memory operation, context window, context budget, eviction.

**Section 3: Three-Tier Memory Model**

**3.1 Active Context** (always available)
- Contains: most recent messages from the current thread, thread metadata, participant list with capabilities
- Scope: shared across all thread participants (per D-16)
- Delivery: included in every context frame
- Size: bounded by `max_context_frame_size` (server-configurable, recommended default 32KB)
- Not explicitly queryable -- it IS the current working context

**3.2 Conversation Memory** (queryable)
- Contains: full message history of the current thread
- Scope: shared across all thread participants (per D-16)
- Queryable via `ainm.memory.query` with tier "conversation"
- Query support: text search across message content, time-range filtering, sender filtering
- The server MAY generate and cache conversation summaries for efficient context frame assembly

**3.3 Archival Memory** (persistent, per-participant)
- Contains: structured facts (key-value pairs), user preferences, cross-conversation knowledge
- Scope: per-participant -- each agent/user has their own archival store (per D-16)
- Operations: store, query, evict via `ainm.memory.store/query/evict`
- Fact schema: `key` (string, dot-namespaced like "user_preference.timezone"), `value` (string or JSON), `tags` (array of strings for categorization), `stored_by` (identity of who stored it), `stored_at` (ISO 8601 timestamp)
- To share archival knowledge with other participants: post a message to the thread (making it part of shared conversation memory)

**Section 4: Context Frame** -- Per D-14, when an agent joins a thread or is @-mentioned, the server delivers a structured context frame via `ainm.context.frame` (JSON-RPC notification, server to client).

Context frame schema:
```json
{
  "thread_id": "...",
  "frame": {
    "active_context": {
      "recent_messages": [
        {
          "id": "...",
          "from": "...",
          "timestamp": "...",
          "summary": "..."
        }
      ],
      "window_start": "ISO-8601",
      "message_count": 15
    },
    "conversation_summary": "...",
    "archival_facts": [
      {
        "key": "...",
        "value": "...",
        "stored_by": "...",
        "stored_at": "..."
      }
    ],
    "participants": [
      {
        "identity": "...",
        "type": "human|agent",
        "presence": "..."
      }
    ]
  }
}
```

Context frame assembly priority (per Pitfall 3):
1. Recent messages: 50% of budget
2. Conversation summary: 20% of budget
3. Archival facts (agent's own): 20% of budget
4. Participant list + capabilities: 10% of budget

`max_context_frame_size`: server-configurable, recommended default 32KB. Server communicates this during capability negotiation.

**Section 5: Memory Operations (JSON-RPC Methods)**

**5.1 ainm.memory.store** (request/response)
Direction: client -> server
Params: `thread_id`, `tier` ("archival" only -- active and conversation are managed by server), `fact` object with `key`, `value`, `tags`
Response: `{ stored: true, fact_id: "..." }` or error
The server validates the fact schema and enforces storage quotas.
Store to "conversation" or "active" tier returns error -32051.

**5.2 ainm.memory.query** (request/response)
Direction: client -> server
Params: `thread_id`, `tier` ("conversation" or "archival"), `query` (string -- text search), `limit` (integer, default 10, max 100), `offset` (integer, default 0), `time_range` (optional object with `start` and `end` ISO 8601), `from_identity` (optional, for conversation tier -- filter by sender)
Response: `{ results: [...], total: N, has_more: boolean }`
For conversation tier: results are message summaries (id, from, timestamp, summary text)
For archival tier: results are fact objects (key, value, tags, stored_by, stored_at)
Memory queries are PRIVATE -- not visible to other thread participants (per RESEARCH.md Open Question 3).

**5.3 ainm.memory.evict** (request/response)
Direction: client -> server
Params: `thread_id`, `tier` ("archival" only), `fact_id` (string) or `key` (string) -- identify what to remove
Response: `{ evicted: true }` or error
Only the participant who stored a fact (or the server) can evict it.

**5.4 ainm.context.frame** (notification)
Direction: server -> client
Delivered automatically when: (1) agent joins a thread (ainm.thread.join response), (2) agent is @-mentioned in a thread they are already in, (3) server determines context refresh is needed (implementation-defined).
The context frame is NOT a thread message -- it is a private notification to the specific participant.

**Section 6: Capability Negotiation** -- The `ainm.initialize` handshake capabilities object adds:
- `memory.conversation` (boolean): Server supports conversation memory queries
- `memory.archival` (boolean): Server supports archival memory store/query/evict
- `memory.maxContextFrameSize` (integer): Maximum context frame size in bytes
If `memory.archival` is false, `ainm.memory.store` and `ainm.memory.evict` return error -32050.

**Section 7: Retention and Eviction Policies** -- Server-managed policies (Claude's discretion):
- Active context: no explicit retention -- always current thread state
- Conversation memory: retained for the lifetime of the thread. Servers MAY archive old threads.
- Archival memory: server-configurable retention. Recommended defaults: max 1000 facts per participant, max 100KB per participant. Server MAY evict oldest facts when quota exceeded (LRU). Server SHOULD notify the participant when approaching quota (80% threshold) via a system message.

**Section 8: Error Handling** -- Error code range -32050 to -32059:
- `-32050`: Memory tier unavailable (server does not support requested tier)
- `-32051`: Invalid tier for operation (e.g., store to conversation tier)
- `-32052`: Storage quota exceeded (archival memory full)
- `-32053`: Invalid query (malformed query parameters)
- `-32054`: Fact not found (evict with invalid fact_id/key)
- `-32055`: Permission denied (evicting another participant's fact)

**Section 9: Security Considerations** -- Memory operations are private exchanges between participant and server, NOT thread messages. Other participants cannot see what queries an agent makes. Archival facts stored by one participant are invisible to others (per D-16) -- agents must explicitly share knowledge by posting to the thread. Context frames may contain sensitive information (recent messages, user preferences); they MUST only be delivered to the requesting participant over the authenticated WebSocket session. Servers MUST NOT include other participants' archival facts in a context frame.

**Section 10: Examples** -- Full examples: (1) Agent receives context frame on thread join. (2) Agent stores a user preference as archival fact. (3) Agent queries conversation memory for earlier discussion. (4) Agent queries archival memory for user preferences.
