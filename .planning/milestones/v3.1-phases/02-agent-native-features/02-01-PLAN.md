Create `spec/streaming.md` following the Phase 1 spec document template: Overview, Terminology, numbered core sections, Error Handling, Security Considerations, Examples/References.

The specification MUST cover these sections (in order):

**Section 1: Overview** -- Streaming enables agents to deliver responses token-by-token in real-time. The streaming lifecycle follows a Start-Delta-End triplet. Streaming events are ephemeral JSON-RPC notifications on the WebSocket connection, NOT persistent signed messages. The collapsed result at stream-end IS a persistent signed message. Reference transport.md for the WebSocket binding and security.md for signing.

**Section 2: Terminology** -- Define terms: stream, stream lifecycle, stream-start, content delta, stream-end, block layout, block index, collapse, ephemeral event, stream_id.

**Section 3: Streaming Lifecycle** -- Three phases:
1. **Stream Start** (`ainm.stream.start`): JSON-RPC notification. Params: `stream_id` (UUIDv7), `message_id` (UUIDv7 -- the ID the collapsed message will use), `from` (sender identity), `thread_id`, `timestamp`, `blocks[]` (array of `{type, version, source}` declaring the full block layout). Block layout is IMMUTABLE for the stream duration (per D-03). Clients render placeholders for all declared blocks immediately.
2. **Content Delta** (`ainm.stream.delta`): JSON-RPC notification. Params: `stream_id`, `block_index` (integer referencing position in blocks[] from stream-start, per D-04), `delta` (string -- 1 to few tokens per D-01). Only TextBlock and CodeBlock are streamable in v1. For CodeBlock deltas, include optional `language` field on first delta for that block.
3. **Stream End** (`ainm.stream.end`): JSON-RPC notification. Params: `stream_id`, `status` ("completed" or "cancelled").

**Section 4: Collapse Semantics** -- When status is "completed": server assembles all accumulated deltas into a permanent signed message (same format as `ainm.message.deliver` from transport.md). The permanent message uses the `message_id` from stream-start, carries the fully assembled `content[]` array with complete block payloads, and includes `metadata.stream_id` for audit trail. Clients replace the streaming placeholder with the permanent message. When status is "cancelled": partial content is preserved with `metadata.cancelled: true` on the message. The server signs and delivers the partial message.

**Section 5: Client-Initiated Cancellation** -- `ainm.stream.cancel` is a JSON-RPC request (has `id` field, expects response). Params: `stream_id`. Server responds with success and sends `ainm.stream.end` with `status: "cancelled"`. Partial content preserved per Section 4. There is NO server-initiated cancellation (per D-02).

**Section 6: Streaming Errors** -- `ainm.stream.error` is a JSON-RPC notification. Params: `stream_id`, `code` (integer), `message` (string), `partial_preserved` (boolean). Error code range: -32040 to -32049. Define specific codes:
- `-32040`: Stream not found (invalid stream_id)
- `-32041`: Invalid block index (delta references index outside declared layout)
- `-32042`: Stream already ended (delta after end/error)
- `-32043`: Agent generation error (LLM failure mid-stream)
- `-32044`: Stream timeout (server-enforced maximum stream duration)
When `partial_preserved: true`, the partial content is delivered as a cancelled message with error metadata. When false, no message is created.

**Section 7: Parallel Multi-Block Streaming** -- Per D-03, agents CAN stream into multiple blocks simultaneously. The stream-start `blocks[]` array declares all blocks upfront. Deltas can arrive for any block_index in any order. Clients MUST buffer and render deltas for each block independently. Example: an agent streaming a text explanation (block_index 0) and a code snippet (block_index 1) simultaneously.

**Section 8: Capability Negotiation** -- The `ainm.initialize` handshake (transport.md Section 4.3) capabilities object adds: `parallelStreaming` (boolean, client supports multi-block streaming). If false, agents SHOULD limit to single-block streams. The existing `streaming` capability flag controls whether streaming is supported at all.

**Section 9: Security Considerations** -- Streaming deltas are ephemeral and authenticated by the WebSocket session (established during `ainm.initialize`), NOT individually signed. This is critical for performance (per RESEARCH.md Pitfall 2). Only the collapsed message at stream-end is signed with Ed25519. Clients MUST NOT trust delta content as verified until the signed collapsed message arrives. If the signed collapsed message does not arrive (disconnect), clients SHOULD mark the streamed content as unverified.

**Section 10: Error Handling** -- Error code table (-32040 to -32049). Behavior on each error. Recovery procedures.

**Section 11: Examples** -- Full end-to-end streaming example: stream-start with 2 blocks (text + code), 6-8 deltas alternating between blocks, stream-end completed, and the resulting collapsed signed message. Also: cancellation example and error-mid-stream example.

Style: RFC-keyword prose ("MUST", "SHOULD", "MAY") with inline JSON examples. Match the tone and depth of `spec/transport.md` (the longest Phase 1 spec at ~850 lines). Target 500-700 lines.
